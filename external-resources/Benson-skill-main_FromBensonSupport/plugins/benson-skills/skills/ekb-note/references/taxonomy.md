# EKB 歸檔與分類規範（taxonomy）

> 寫筆記前，先用這份決定「歸到哪個資料夾（`parent_id`）＋ 掛哪些標籤」。
> 目標：**AI 寫筆記時就歸好位，人不用再手動拖拉。** 新筆記絕不留在根層。

## 0. 為什麼（設計哲學）
EKB 是「慢慢長出來的個人知識庫」——沉澱既定事實、收集文獻、囤待研究的東西。
分類該在「寫的當下」就歸好，人只做偶爾修正；手動拖拉樹在 200+ 篇時不擴展。

## 1. 操作模型（4 個維度，互相獨立）
| 維度 | 用什麼 | 例 |
|---|---|---|
| **主題** | 資料夾（`parent_id` 樹）| 00 各專案 / 01–08 跨專案知識 |
| **型態** | 型態詞直接當標籤（**不加任何前綴**）| 系統分析 / 系統設計 / 會議紀錄 / 報價 / 測試 / SRS |
| **狀態** | `待研究` 標籤 | 收集未消化 → 進「📚 待研究」Notebook |
| **內容** | 內文 ＋ 上傳附件（自動萃取可搜） | PDF / 圖 / 影音 |

主題用資料夾，型態/狀態用標籤——**同一篇可同時是「02 技術 ＋ 影音 ＋ `待研究`」**。
⚠ 型態標籤**直接寫詞**（系統分析、會議紀錄…），**不要加 `doctype:` 之類前綴**；也**別掛太泛的型態**（如「技術文件」「手冊」——幾乎每篇都是，只會變雜訊 hub）。
重點：**按「主題」分資料夾、按「格式」掛標籤**。不要再用「YouTube 資料夾」這種按格式分的資料夾。

## 2. 核心歸檔鐵則（最重要）
判斷口訣：**「換個專案還用得到、且不是任何單一案的交付物嗎？」**

1. **屬於某專案** → `00 {專案}`（該案的資安報告/報價/手冊/SRS/設計/測試… 全歸該案）
2. **不屬於任何專案、但重要的跨領域議題** → `01–08`
3. **不確定** → `09 草稿・暫存`

「資安」範例：某案的弱掃報告 → 回那案的 `00`；但「ISMS 怎麼做 / 弱掃方法 / 資安議題研究」這種跨專案知識 → `04 資安`。

## 3. 01–09 定義（Benson 定版）
| 號 | 資料夾 | 收什麼 |
|---|---|---|
| 00 | {各專案} | 屬於該專案的一切交付物（見 §5 專案內結構） |
| 01 | 方法・範本・培訓 | SA/SD/PM 方法論、文件範本、報價/估價範本、SDLC、培訓 |
| 02 | 技術・AI 研究 | 技術選型、AI 模型/工具、框架、維運/工具通用 know-how、研究 |
| 03 | 提示詞・Loop 工程 | 提示詞庫 ＋ loop/harness/agent 工程、context 工程 |
| 04 | 資安 | 資安議題/方法/ISMS/滲透/弱掃 know-how ＋ 帳密憑證 |
| 05 | （預留） | 之後出現「重要又不屬專案」的議題再拉一號（例：GIS/圖台、IoT/感測） |
| 06 | （預留） | 同上 |
| 07 | （預留） | 同上 |
| 08 | 學習・文獻 | 外部學習、講座/某教授、YouTube 等影音知識；多半同時掛 `待研究` |
| 09 | 草稿・暫存 | inbox / 不確定 / 待整理 |

## 4. 怎麼把筆記放進資料夾（parent_id 解析）
資料夾本身就是一篇 `parent_id=NULL` 的筆記，標題像「04 資安」。設 `parent_id` 步驟：
1. 依 §2 鐵則判斷目標資料夾名稱。
2. 取得該資料夾 note id：`GET /api/notes.php?list=1&q={如 "04 資安"}` → 比對 title 完全相符 → 拿它的 id。
   - 專案類先 `GET /api/projects.php` 對到專案，再找對應的「00 {專案}」資料夾筆記。
3. POST/PATCH 時帶 `parent_id={那個id}`。
4. **找不到對應資料夾**（議題還沒建資料夾、或全新專案）→ 先問使用者要不要建，或暫掛 `09 草稿` 並告知。**絕不留根層（`parent_id=NULL`）。**

> 別硬寫死 id（資料夾會搬/改名）；**以名稱為契約，每次查**。
> 已知資料夾 id（查證參考，可能變動）：01=292、02=293、03=294、09 草稿=299；`04 資安` / `08 學習・文獻` 等以實際查到為準（結構整理後才齊）。

## 5. 專案內結構（00 底下）
每個專案的交付文件，可參照公司標準文件架構 `progress/document_config.php`（前置作業/SDLC文件/會議記錄/資安管理/行政變更/系統開發/技術文件/操作手冊/測試/部署維運/Demo…）。
**但 EKB 端先別硬建三層子資料夾**——用 `doctype:` 標籤輕量標註即可（要看「所有 SRS」用 Notebook 依標籤自動撈，比挖資料夾快）。專案大到值得時再開子資料夾。

## 6. 型態標籤（跟主題資料夾正交）
依文件型態掛一個型態標籤，**直接寫型態詞、不加任何前綴**（❌ 不要 `doctype:`）：
`系統分析` `系統設計` `會議紀錄` `報價` `測試` `規格` `SRS` `文獻` `教學` `資料庫設計`
- ⚠ **別掛太泛的型態**（「技術文件」「手冊」幾乎每篇都是 → 雜訊 hub，不要）。
- 沿用既有——先 `GET /api/tags.php` 比對，別建近義（見標籤治理鐵則）。

## 7. 待研究 狀態 ＋ Notebook
收集「還沒消化的文獻/講座/影片」（如「X 教授講了一篇…」）：
- 歸到對的主題資料夾（多半 `08 學習・文獻`，或該議題的 `01–04`）
- 加掛 `待研究` 標籤
- 由 Notebook「📚 待研究」依 `待研究` 規則自動匯集成清單 → 使用者哪天有空打開就是 reading list
- 消化完 → 移除 `待研究`，把心得補成正式內容（沉澱成「既定事實」）

## 8. 寫入前一句話（沿用既有鐵則）
POST 前先告訴使用者：
「我要把這存成筆記：歸到 **{00 xx / 01–08 / 09}**、型態 {X}、{待研究?}、標籤 {Y}、來源 {Z}」再寫。
