# 專案開發管理技能

這份技能定義了 Benson 團隊在處理軟體開發專案時的標準工作流程。核心理念：**討論完就要有產出，不要只是聊聊。**

## 一、工作流程

每個新專案或模組的討論，遵循以下順序：

1. **讀需求文件** — 先完整讀過需求文件（報告、規格書、會議紀錄等），提取所有已確認和待釐清的事項
2. **建結構化清單** — 把事項分類整理成表格，不要只列問題，已確認的也要列出來
3. **逐項討論** — 跟使用者一項一項過，記錄決策
4. **建 Notion 追蹤** — 把最終結果同步到 Notion，建立可追蹤的頁面結構
5. **定義開發順序** — 根據技術依賴關係排出先後順序，不要留「待決定」

## 二、Notion 頁面結構規範

所有專案在 Notion 的組織方式必須一致：

```
專案名稱（頂層頁面）
├── 系統 A（系統說明頁）
│   ├── 開發事項總表（子頁面）
│   ├── UX 操作流程（子頁面）
│   └── 任務分工表（資料庫，若有）
├── 系統 B（系統說明頁）
│   ├── ...
```

### 系統說明頁格式

每個系統/模組的主頁面只放簡要說明，格式參考：

```
系統全名 — 開發管理
**主要模組：** 模組 A + 模組 B
**技術架構：** 框架 / 語言 / 資料庫 / 其他
**關聯系統：** 獨立 or 與 XX 整合
**開發階段：** Phase 0 → 1 → 2 → ...
---
## 相關文件
- 需求文件名稱
- 模擬畫面（若有）
## 說明
以下子頁面追蹤所有開發事項。
[子頁面連結]
```

重點：**主頁不放細節，細節放子頁面。** 這樣結構才乾淨。

### 開發事項總表格式

用三種狀態標記每個事項：

| 標記 | 意義 | 說明 |
|------|------|------|
| ✅ | 已確認 | 需求文件明確定義的、或討論後確認的 |
| ❓ | 待釐清 | 文件沒寫清楚、需要進一步討論的 |
| 🔴 | 甲方須提供 | 需要甲方交付資料、文件、權限等 |

事項按主題分章節，每章節內區分「已確認」「甲方須提供」「待釐清」三塊。甲方須提供的用表格列出，包含：編號、資料名稱、接受格式、狀態。

## 三、開發順序規劃原則

不要留「待決定」，直接根據以下邏輯排序：

1. **技術依賴** — 被依賴的先做（資料層 → 核心演算 → 前端介面）
2. **資料就緒度** — 資料需求較單純的模組先做
3. **可驗證性** — 能獨立測試的模組先做
4. **複用性** — 會被其他模組呼叫的元件先做

每個 Phase 要列出：順序編號、工作項目、產出物、依賴關係。

## 四、技術決策記錄

當使用者確認技術選型時，立即記錄到 Notion 系統架構表，格式：

| 項目 | 決定 | 狀態 |
|------|------|------|
| 前端框架 | XXX | ✅ 已確認 |
| 後端語言 | XXX | ✅ 已確認 |
| 資料庫 | XXX | ✅ 已確認 |
| ... | ... | ... |

## 五、溝通風格

- **繁體中文**為主
- **精簡不廢話** — 不要長篇大論解釋為什麼，直接給結論
- **主動建議** — 不要等使用者問，覺得該做什麼就直接提
- **先做再說** — 能直接執行的不要先問「要不要我幫你...」
- 使用者說「釐清」就是要逐項過，不是要你寫一篇分析文
- 討論完一個主題就立刻同步到 Notion，不要等全部討論完

## 六、常見模式

### 從需求文件啟動新模組

使用者給一份需求文件 → 你應該：
1. 讀完文件
2. 列出所有事項（已確認 + 待釐清 + 甲方須提供）
3. 建 Notion 頁面（先建系統說明頁 → 再建子頁面）
4. 逐項跟使用者確認

### 使用者提供技術決策

使用者直接告訴你用什麼技術 → 你應該：
1. 立刻記錄到 Notion 系統架構表
2. 如果有相關影響（例如這個選擇影響到某些待釐清事項），順便標記

### 補充 UX 流程

使用者要求補充操作流程 → 你應該：
1. 根據已知的模組功能，定義操作步驟（Step 1, 2, 3...）
2. 列出對應的畫面清單
3. 如果有 HTML prototype，對照畫面編號
4. 建成 Notion 子頁面

### 資料格式與來源整理

遇到資料輸入相關的事項 → 表格要包含：
- 資料名稱
- 接受格式（具體到副檔名）
- 來源（API / 甲方提供 / 系統內建）
- 狀態（🔴 未提供 / ✅ 已取得）

## 七、注意事項

- **不要把所有東西塞在同一頁** — Notion 頁面太長會難以維護，適時拆成子頁面
- **表格比條列好** — 需要追蹤狀態的事項用表格，純說明才用條列
- **編號要連續** — 跨章節的事項編號要連續，方便引用（例如 #35 指的就是某個具體參數）
- **每個系統獨立** — 即使共用專案，每個系統/模組在 Notion 上都是獨立的頁面結構
