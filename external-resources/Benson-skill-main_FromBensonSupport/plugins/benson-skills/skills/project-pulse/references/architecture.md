# project-pulse 架構設計（設計聖經）

> 本檔是整個 skill 的「為什麼」。SKILL.md 是「怎麼做」，這裡是「為何這樣做」。
> 源自 2026-06-13 與 Benson 的完整需求討論（從「進度儀表板」一路修正到「四層分層問答」）。

---

## 0. 為什麼有這個 skill

Benson 同時做多個政府／企業專案，每 1–2 週追一次進度，會「順口問」某專案的某個主題 —— 例如「桃園水情的路面淹水機制是什麼？有什麼特色？用預測雨量嗎？」

痛點：同一個專案的資料**散在五個地方**（EKB / EIP / LINE / Outlook / 專案資料夾），要快卻得自己一個個翻。本 skill = 把這些聚成「**問一句、分層答**」的單一入口。

**踩過的兩個錯誤方向（別重蹈）：**
1. ❌ 第一版做成「專案管理儀表板」（一堆工項燈號）— Benson：「這不是我要的，太偏工項。」
2. ❌ 第二版「四個源全撈來平鋪混在一起」— Benson：「資料來源應該統一 EKB 到筆記找，LINE 只是沒定案的事情。」

→ 正解是下面的**四層分層 + EKB 為主 + 漸進式**。

---

## 1. 核心洞察：資料按「成熟度」分層

Benson 的資訊不是平的，是**按成熟度分層**的，每層住在不同地方：

| 層 | 性質 | 住哪 | 成熟度 |
|---|---|---|---|
| 📗 既定事實 | 定案、整理過的知識 | **EKB 筆記** | ✅ 最硬（當定論） |
| 📋 指派中 | 誰在做、什麼狀態 | **EIP 工項** | 🔵 進行中 |
| 💬 討論中 | 還在喬、未定案 | **LINE / Outlook** | ⚠️ 流動 |
| 📁 研究中 | 開發中、超不明確 | **專案資料夾** | 🔬 最軟 |

**越上面越硬（定案），越下面越軟（流動）。** 工具回答時每層貼成熟度標籤，使用者一眼分得出「哪些能對外講、哪些還要拍板」。

---

## 2. 結晶比喻（為什麼 EKB 是主、LINE 是輔）

```
LINE / Outlook  →   handover   →   EKB
（溶液·還在反應）  （結晶中·半成品）  （晶體·定案）
```

- Benson 的工作流：討論在 LINE/Outlook 發生（吵、喬、來回）→ 拍板後用 `meeting-record` / `ekb-note` **沉澱進 EKB**。
- 所以 **EKB 是「結晶」**（已定案知識），LINE/Outlook 是「溶液」（還在反應）。
- **查知識就該喝結晶水（EKB），不該撈整缸溶液（原始對話）** —— 撈溶液又雜又會跨案污染。

---

## 3. handover 的定位（不是第五個源）

handover **不是內容的家**，是「**AI 的工作記憶 / 工作層**」，跟四層真相是不同維度：

- **作用①交班**：跨 session 記「做到哪、下一步」，讓 AI 換 session/裝置接得上。
- **作用②訊號加工**：把 LINE 原始討論挖成結構化 `decision/blocker/commitment` 暫存（= 上面結晶比喻的「結晶中·半成品」）。
- **對使用者透明**：他不用把 handover 當第五個地方去翻。skill 用它當後台（記住查過什麼、不重挖）。

---

## 4. 漸進式查詢（Benson 最在意的「快」）

> 鐵則：**先打 EKB、秒回第一段，不要一次四層全撈。**（Benson：「找一大輪太久了。」）

- **第 1 段（預設·秒回）**：只打 EKB。有就整理成定案答案；0 命中就老實說查無、問要不要往下。多數問題這段就夠。
- **第 2 段（按需展開）**：使用者要「還在喬什麼／誰在做／最新討論」才撈 EIP/LINE/資料夾。
- **第 3 段（要報告才做）**：render 成暖色分層 HTML、推 Discord。

EKB 有 `project_id` 過濾、是結構化定案知識，撈起來又快又準；LINE 要挖一大堆原始對話、慢又會跨案污染 —— 所以「先 EKB、後其他」既快又對。

---

## 5. 絕對鐵則：不唬爛

- **只講資料裡真有的。** 查無就說查無，**絕不用訓練知識瞎掰**。
- 實測：問「農工 稻熱病預測」→ EKB/EIP/LINE 三層全 0 命中。正解＝「查無此題，農工實際在做楊梅田水位/影像辨識」；**錯解**＝掰一套「稻熱病通常用溫濕度感測+AI 模型」（那不是 Benson 系統在做的）。
- Benson 的報告要給長官／甲方看，**可信度 > 完整度**。「查無」是有用的答案（揭露知識缺口）。

---

## 6. 組合技能（指揮 ↔ 樂手）

本 skill 是「**組合劑**」（Benson 原話），不重造功能，調度現有 skill：

| 樂手 skill | 負責的層 |
|---|---|
| `ekb-note` | 📗 EKB 既定事實 |
| `eip-item-builder` | 📋 EIP 工項指派 |
| `eip-line-radar` | 💬 LINE 討論 |
| （檔案掃描） | 📁 專案資料夾 |

**memory 與 skill 的差別**（為什麼值得做成 skill）：memory＝「我應該這樣做」（靠自覺、會漂）；skill＝「每次一定這樣做」（固定流程、撈取腳本寫死、不忘不漂、又快又準）。

- [ ] 查無有老實說、沒唬爛嗎？

- [ ] 專案名有正確解析成 project_id（含別名）嗎？
- [ ] 回覆有明示資料新鮮度嗎？
