# 新手引導式逆向工程 SOP

## 目的

讓不熟悉系統分析或逆向工程的人，能從手邊的程式碼、畫面、規格、操作說明或口述資訊開始，逐步整理出「目前可以證明什麼、可能的設計是什麼、還有哪些問題要確認」。此流程適用於 API、網站、行動 App、批次程式、資料流程、桌面軟體及其他既有系統；任何單一案例只作示範，不得成為 SOP 的固定前提。

主要路徑是：

```text
使用者可提供的材料
    → AI 盤點與追查入口／觸發點
    → 依來源畫出目前流程圖
    → 從流程圖整理設計與規格候選
    → 對照原始規格、使用者認知及程式現況
    → 列出差異、未知與下一步
```

## 對話規則

1. 使用者不用先學會 SSDLC、HTTP、資料庫或逆向工程術語。每次提問使用日常語言，先說明這題為什麼重要。
2. 每一輪最多提出一個需要使用者回答的主要問題。可在同一問題中提供 2–3 個簡短選項和一個可照抄的例子；不要一次列出問卷讓新手填完。
3. 接受「不知道」「手邊沒有」「先跳過」。將其記為未知或缺少材料，再用可讀取的來源繼續；只有該答案會影響安全、範圍或不可逆行為時才暫停相關操作。
4. 優先由 AI 掃描使用者指定目錄和已提供的附件，辨識語言、框架、入口候選、文件、測試及設定。入口不明時，AI 先給出候選及檔案／行號或其他來源，再請使用者確認；不能把尋找入口的技術負擔交給新手。
5. 每個答案後用一兩句話回述「目前確認的內容」及「仍未知的內容」，避免把推論藏在摘要裡。使用者可隨時修正、補充或停止。
6. 若使用者同時提供程式碼和原始規格文件，將規格文件視為一項待比對來源；不能假設它一定比現況新或正確。若兩者版本、內容或日期衝突，並列顯示，待使用者判斷適用基準。

## 證據標記

在分析筆記、圖表旁註、候選規格及結論中，使用下列簡單標籤；每項重要結論至少標一個標籤及來源：

| 標記 | 意義 | 例子 |
|---|---|---|
| `成品可見` | 靜態解析成品 bytes／metadata／CIL | 附 artifact 指紋、位置及 Evidence ID；不是原始碼或實際執行 |
| `歷史紀錄` | 既有 HAR／日誌的錄製行為 | 附錄製版本、環境與範圍；不是本次執行 |
| `程式可見` | 靜態讀取程式碼可直接確認 | 某分支收到欄位 X 後呼叫函式 Y；附檔案與行號 |
| `文件記載` | 附件或既有文件明確寫出 | API PDF 說明成功回應格式；附文件頁碼／章節 |
| `使用者提供` | 使用者回憶、描述或選定的預期 | 使用者表示 Token 期限為六個月 |
| `實際觀察` | 在獲准的指定環境中實際執行後觀察到 | 測試環境實際回應 HTTP 200；附時間、環境及安全遮蔽後的結果 |
| `推論` | 根據多項證據作出的解讀，尚未被直接證實 | 由呼叫順序推測某步驟負責建立工作階段 |
| `未知` | 現有材料無法判斷 | 未找到撤銷流程或正式環境回應 |
| `衝突` | 來源之間互不一致 | PDF 與目前程式使用不同的欄位名稱 |

不要將「使用者期望」改寫成「目前程式行為」，也不要將靜態分析或圖表產出描述成實際執行結果。推論應說明依據，並保留可推翻它的未知項目。

## 逐步引導流程

### 第 1 步：用白話界定要理解的事

詢問使用者目前最想搞清楚哪一個操作、功能或問題，以及最後要拿分析結果做什麼。若使用者已說明，直接回述並請其修正，不重複提問。

可接受的起點包括：某個按鈕、某次使用者操作、API 名稱、資料匯入／匯出、排程、錯誤現象、程式入口候選或一份文件。不要求一開始就提供完整系統。

### 第 2 步：盤點手邊材料

請使用者提供可取得的專案路徑、程式碼、規格 PDF、截圖、日誌、範例請求／回應、資料表定義、測試或部署文件。每輪只追問最有價值的一項缺口。無原始碼時可提供 DLL／EXE／APK／ASAR 或已去識別化 HAR；先依 REA 規則建立來源宣告，不要求補齊原始碼。

在允許讀取的範圍內先自行列出材料清單及無法讀取的項目。提醒使用者遮蔽密碼、Token、個人資料、連線字串及正式環境秘密；不要求提供真實憑證。使用者只有 PDF 或片段時，仍可先做局部分析並標出範圍限制。

### 第 3 步：定位入口或觸發點

AI 先依任務類型找入口。例如：HTTP 路由／Controller、UI 事件／頁面、命令列入口、排程註冊、訊息佇列消費者、資料匯入程序、資料庫 Trigger，或外部服務呼叫點。這些是搜尋方向，不是預設系統一定具備的元件。

提供少量最有可能的候選，每項附檔案、行號、文件章節或搜尋線索，並用白話說明差異。再問一題讓使用者確認要追哪一個操作；如果使用者不知道，依現有描述挑最吻合者繼續，標為待確認。

### 第 4 步：確認環境邊界與可做的驗證

說明本次會先做哪些唯讀分析。若要對服務、資料庫、第三方系統或裝置執行任何測試，先確認目標是本機、測試環境或正式環境，以及使用者授權的動作和範圍。

沒有明確授權時，只做靜態檢視、既有測試／日誌的閱讀及文件比對。正式系統無法測試時，不要求使用者為了完成分析而操作正式系統；把驗證項目列成待辦，仍繼續還原靜態流程。使用者只授權讀取時，不做寫入、登入嘗試、資料變更、壓力測試或其他會觸發副作用的動作。

### 第 5 步：從觸發點追到結果

沿實際證據追蹤主要資料與控制流程，依系統型態記錄適用的節點：觸發者、入口、驗證／授權、條件分支、服務或模組呼叫、資料讀寫、外部依賴、狀態變化、回應／畫面／檔案／訊息，以及錯誤處理。不是每種系統都有 API、資料庫或 Token；不存在的元件不補造。

一次先追一個最小可理解的流程。遇到關鍵分支或決策時，以白話說明程式目前做什麼，再問使用者是否知道該行為的業務原因／預期。答「不知道」就保留未知並繼續，不把沉默當同意。

### 第 6 步：先畫圖，再反推設計

優先用 `diagram-design` 選擇最容易讀懂且適合證據的圖：一般順序用流程圖；有多個角色或系統責任時用 Swimlane；跨元件呼叫順序用 Sequence；資料如何流動用 Data-flow；資料結構有證據時才用 ER／Schema；模組關係用 Architecture／UML Class；有明確狀態轉換時用 State。小範圍 POC 先選一張主圖，不為湊齊圖種而產生無證據圖表。

每張圖都應：

- 標出範圍、起點、終點及主要分支。
- 在節點或圖例中標示證據標籤；提供來源索引，至少能回到檔案與行號、文件頁碼、測試紀錄或使用者回答。
- 將推論、未知和衝突以明顯但易懂的方式標記，不能用看似確定的連線遮住證據缺口。
- 使用適合閱讀的字體與版面；密集流程拆圖或分層，不靠把整張圖縮小來塞內容。

完成圖後，依圖整理「目前實作／流程設計候選」：元件職責、呼叫順序、輸入輸出、資料關係、錯誤分支、安全邊界及外部依賴。圖是來源證據的導覽，不是獨立證據。

### 第 7 步：反推需求並對照原始規格

從可追溯的流程節點整理需求候選，使用一般使用者看得懂的描述，再附驗收情境及來源。將以下類別分開呈現：

- 原始規格明確要求、程式也有證據支持。
- 原始規格有要求、程式目前未找到對應或呈現不同做法。
- 程式目前有行為，但原始規格未說明。
- 使用者希望未來如此，但尚未證明現況如此。
- 來源不完整，暫時無法判定。

需求候選不自動等於已核准需求。未核准之前，不回寫正式正向 SSOT 作為確定規格；依主 Skill 規定先放在逆向候選產物，再經使用者／業務審閱後走正向 Phase 01。

### 第 8 步：回報與下一個最小問題

每個小段落完成時，用固定而精簡的格式回報：

1. **我們目前知道**：最多列幾項有來源的發現。
2. **圖上呈現**：目前流程覆蓋到哪裡、有哪些分支。
3. **還不知道／有衝突**：具體指出缺什麼來源或哪兩個來源不一致。
4. **驗證狀態**：靜態推導、既有測試紀錄或本次實際執行；不得混稱。
5. **下一個問題**：只問最能解除阻塞的一題；若沒有，就先產出可審閱成果。

## 輸出與完成判準

依使用者目標調整產出深度，至少保留一份簡單的流程說明和來源追溯。完整案例可產出入口與資料流圖、設計候選、需求候選、原始規格對照表、未知／衝突清單及建議驗證步驟。

只有在約定範圍已被分析、重要結論能回指來源、未知及衝突已明示、成果已向使用者說明時，才可稱「本次逆向蒐證完成」。並須另外交代哪些內容已做實際驗證、哪些僅為靜態分析、哪些決策仍待業務確認。完成蒐證不代表 POC、正式系統行為、資安或正向 SSDLC 關卡已通過。

## API 類案例的可選檢查清單

只有在本次目標確實是 API 時才使用：呼叫端與用途、方法與路徑、請求欄位、驗證／授權、回應格式與狀態碼、錯誤碼、資料副作用、Token／Session 生命週期、重試／冪等、callback／redirect、限制與版本。缺少程式、規格或實際觀察的項目標為未知；不得把此清單硬套到其他類型的逆向工作。

## REA 與無原始碼逆向

沒有完整原始碼時，先讀 [REA 整合 Skill](../rea/SKILL.md)，依成品、離線紀錄、黑箱目標或文件分流。REA 是選用 provider；只有文件／UI 不強制安裝 REA。來源 manifest 記 `source_available=false`；Phase 03 改做成品與行為蒐證，不能要求完整類別、服務端路由或 DB。

保留既有產物檔名；資料不足時寫未知或空清單並附 coverage，不以檔案存在推定完整。Phase 02 必須讀取 evidence_manifest.json、findings_index.json、unknowns.json、coverage.json；內部無證據時用黑箱節點，不補造 ER／DDL／handler。原始 REA observed 不等於本次執行。

起點先執行 `python scripts/check_no_source_evidence.py --project <專案路徑> --inputs-only`；交接時由 reverse integrity／Mode E 檢查證據與覆蓋。仍按 Phase 03→02→01 候選流程及既有正向核准關卡推進。

無原始碼新手直接使用 [REA 新手指南](../rea/references/getting-started.md) 的提示。先說明來源、工具準備與交付物；由 AI 填 manifest，不能要求新手自行建立完整證據 schema。
