# 無原始碼逆向工程：SSDLC 整合規則

此規則由 REA Skill 與既有 reverse_engineering Skill 共用，IO 契約及檢查器已納入無原始碼分流。REA 是可選 provider；無原始碼模式不以安裝 REA 為前置條件。

## 模式選擇

開始時記錄 source_available=false，盤點可用材料及允許操作，再依證據分流：

| 可用材料 | 分析方式 | 可成立的結論與界限 |
|---|---|---|
| DLL／EXE／APK／ASAR | 格式辨識後使用適用 REA provider | 靜態結構、引用及可見控制線索；反編譯結果非原始碼 |
| HAR／SAZ／log／設定檔 | 離線擷取契約與行為紀錄 | 特定版本與錄製情境的行為；不是目前服務驗證 |
| 只有可操作 UI／遠端 API | 已確認範圍的黑箱觀察與測試工具 | 可見輸入、輸出及副作用；REA 不自動取得內部實作 |
| 只有手冊／截圖 | 文件分析工具 | 文件宣稱與設計候選；不是實際執行證據 |
| 加密／混淆／不支援格式 | 保存限制、改以可用外部證據 | 不預設能還原，不以空結果推論功能不存在 |

先使用離線資料；如需啟動目標、安裝、登入、發送請求或修改資料，檢查既有授權是否涵蓋該操作。範圍已明確時直接執行；未涵蓋時先完成其餘分析並列出待確認操作。

## Phase 03：成品與行為蒐證

將無原始碼模式的 Phase 03 定位為實作證據蒐集，而非保證還原程式碼。

- 保存來源清單、SHA-256（適用檔案）、版本、格式、provider、操作、環境、分析範圍與限制。
- 每項 finding 保留 evidence_id、來源位置與證據類別；區分文件宣稱、靜態觀察、歷史紀錄、本次受控執行、推論。
- REA observed 不等同本次執行。保留 authority、operation、environment、relationship_coverage，不能單靠 confidence 轉換狀態。
- 表示 class/function、route、dependency、table 的輸出各自宣告 coverage。實際未觀察到時寫 unknown／not_observed 與理由；有理由確定不適用才寫 not_applicable。空清單只表示沒有列出，不能代表不存在。
- 客戶端 URL 不保證服務端路由目前可用；傳輸物件不等同資料表；字串／函式名稱不等同實際可到達行為。

## Phase 02：外部模型與候選內部模型

先以證據建立使用者、客戶端、遠端服務、外部整合、資料流及可確認信任邊界。服務端可呈現為黑箱節點；內部資料庫、服務與控制位置保持未知。可建立候選模型，但以推論標記並列出替代解釋與驗證方式。

安全基準已啟用，或使用者明確要求／選取威脅建模時，威脅模型為必要交付物；其餘為選用。選用 REA 本身不觸發必要建模。

無原始碼仍可建模，但每項威脅應有：資產／信任邊界、前置條件、攻擊假設、影響、支持證據、未知控制、驗證方式及狀態。區分待驗證威脅與已確認弱點；未看到控制不代表控制不存在。

優先依實際情境檢視身分與授權、資料輸入與輸出、本機敏感資料、外部通訊、更新與供應鏈、日誌與可觀測性。STRIDE 用於逐邊界檢視，不為填滿六類而捏造適用威脅。

## Phase 01 與正向交接

可觀察到的現況轉成需求候選，不直接當應有規格。記錄文件與行為衝突、未知與需要業務決議的項目。核准後才進正向 SSOT；執行成功不自動寫 approved、evaluator.passed 或 Baseline。

無原始碼案件可只交付評估、替代系統需求或外部測試；不要暗示一定能修補原產品。修復可以是供應商處理、配置／外部防護或重建；其可行性需獨立確認。

## IO 與檢查器

無原始碼模式使用 `inputs/reverse_input_manifest.json` 宣告來源。現有 source 模式無須新 manifest，維持相容；新無原始碼案件不可省略 manifest。Phase 03 的 `scan_report.json.source_available=false` 也會觸發此檢查，防止漏交來源宣告。

Phase 03 新增 evidence_manifest.json、findings_index.json、unknowns.json、coverage.json；Phase 02 讀取這四份資料並建立自己的 coverage.json。詳細欄位與範例見 [provider-contract.md](provider-contract.md)。`check_no_source_evidence.py` 驗證來源指紋、ID 連結、未知關聯及產物覆蓋，並已接入 reverse integrity 與 Mode E。檢查器驗證的是靜態契約，不能證明分析結論、授權或安全控制正確，也不取代人工審閱。

## 行為驗收案例

| 案例 | 預期結果 | 設計原因 |
|---|---|---|
| 只有 native EXE，沒有適用引擎 | 盤點與限制可交付，內部結構未知 | 防止宣稱所有成品可反編譯 |
| 只有 HAR，未觀察到 DB | 可建外部 DFD；不產生虛構 ER／DDL | 防止用網路欄位推論儲存結構 |
| DLL 有管理員判斷字串 | 記錄靜態線索，服務端授權待驗證 | 防止把字串當控制有效證據 |
| 正常使用者錄製登入成功 | 不宣告越權／撤銷／到期控制通過 | 正常路徑無法覆蓋安全負向情境 |
| 混淆導致呼叫圖不完整 | coverage=partial，保留未解節點 | 防止空結果被解讀為不存在 |
| 只有 UI，沒有 binary | 使用黑箱工具與文件；REA 非必要 | 防止將無原始碼誤等同有可分析成品 |
| 僅啟用 REA／另明確選建模 | 前者建模選用，後者必要 | 保留使用者確認的政策 |
| 歷史版本已驗證，本次版本變更 | 舊證據保留，新增影響分析與待重驗項 | 防止跨版本沿用通過結論 |

上述案例為整合設計的驗收情境，尚未代表 REA 實機測試結果。
