# BCP 演練計畫書產生器（bcp-drill-doc）

本 skill 將今天與 Benson 協作撰寫「觀測站資料展示平台 營運持續計畫」的整套經驗固化，供未來任何政府 ISMS／稽核相關 BCP 演練文件專案沿用。

---

## 一、觸發關鍵字

啟用本 skill 的訊號：

- **BCP** / 營運持續計畫 / 持續運作計畫 / BCP 演練
- 演練紀錄表 / 演練計畫書 / 演練文件 / 備援演練
- ISMS 演練 / 災害還原演練 / 災害復原演練
- 桌上型演練 / Tabletop Exercise
- 顧問退件 / 演練被退 / 稽核挑 / 審核未過
- 要求撰寫、檢視、修訂 BCP 相關 docx

---

## 二、三種模式

依使用者意圖選擇：

### 模式 A：從零產生（gen）
使用者說「幫我寫 XX 系統的 BCP 演練計畫」「建新的演練紀錄表」。
→ 執行「一次問完」問卷 → 產 docx + 架構圖。

### 模式 B：Review 既有文件（review）
使用者說「幫我看這份」「幫我檢查」「顧問退件了幫我看哪裡有問題」。
→ 讀 docx → 跑 `review_bcp_docx.py` → 按 🔴🟡🟢 列清單。

### 模式 C：增量 Patch（patch）
使用者說「按剛剛 review 的結果幫我改」「一次 gen 一個新版修好」。
→ 讀 docx + 修正清單 → 跑 `patch_bcp_docx.py` → 輸出修訂版（保留原格式）。

模式選定後再執行對應 SOP。

---

## 三、SOP — 模式 A（從零產生）

### Step 1：一次問完問卷（⚠️ 不可擠牙膏逐題追問）

列出所有需要的輸入，用 ★（必答）◇（有就更好）分群，一次貼給使用者：

```
★ 一、系統與版本
1. 系統正式名稱？（會出現在封面與所有章節）
2. 版號規則？（甲方有指定固定版號嗎？例如必須 V3.0）
3. 演練日期？（115 年 N 月 N 日，民國年）
4. 演練地點？

★ 二、技術環境（用台灣用語，不要講「技術棧」）
5. Web／AP 技術：IIS + .NET Framework？（版本若不確定，可寫「由資訊管理科統一配置與維護」迴避）
6. 資料庫：SQL Server 版本？定序？安裝光碟誰提供？
7. 架構類型：【一台主機同時跑 AP+DB】／【兩台分離（WEB + DB）】？
8. 是否有對外網站／展示前端？還是只有資料接收服務？
9. 網站 URL／SSL 憑證有無？
10. IIS 額外模組？（URL Rewrite／ARR／其他）

★ 三、RTO／RPO／MTPD
11. MTPD（最大可容忍中斷時間）小時數？
12. RTO（復原時間目標）小時數？
13. RPO（復原點目標）小時數？
14. 備份策略（每 N 日一次完整備份？保留幾代？）
15. 異地備份位置？【情境中是否也同時毀損】？
    → 若是，會用「RPO 最壞情境超標說明」三段套路

★ 四、人員與單位（政府單位稱呼要正確！）
16. 承辦單位人員（姓名／職稱／分機）？
17. 資訊管理科人員？（⚠️ 不是「資訊室」「資料治理科」，水保署正確稱呼是「減災監測組資訊管理科」）
18. 廠商人員？含 PM？PM 要加進職責表嗎？

★ 五、通報流程
19. 資通安全事件通報流程沿用現有嗎？還是要重寫？

★ 六、銷毀方式
20. VM／備援主機銷毀方式？可以用「VM 申請表所載使用期限」做書面佐證嗎？

◇ 七、文件範疇
21. 這份是純「計畫書」還是包含「佐證」？
    → 純計畫書可省略 Log 匯出、銷毀紀錄表等佐證步驟

◇ 八、架構圖
22. 要哪種產出方式？
    [1] image-gen skill（AI 生圖，精美）
    [2] SVG（可編輯，推薦）
    [3] PNG（matplotlib 泳道圖）
    [4] 我自己有圖
23. 有幾個泳道？代表性外點站名稱？資料接收管道（HTTPS／MQTT）？

◇ 九、系統服務說明（回應顧問退件常見第 2 點）
24. 服務對象（內部單位／外點站／研究人員）？
25. 服務重要性（為何是關鍵系統）？
26. 中斷影響（給誰造成什麼衝擊）？
```

收到回答後彙整成 config dict，再進 Step 2。

### Step 2：產生 docx

1. 讀 `checklist/必備欄位.md` 確認章節齊全
2. 架構類型（單機 AP+DB／雙機 WEB+DB 分離）寫進 config，`gen_bcp_docx.py` 依 config 直接組裝章節（程式產生，無 template 檔）
3. 執行 `scripts/gen_bcp_docx.py --config config.json --output ./output/XXX.docx`
4. 執行 `scripts/gen_arch_diagram.py --mode <svg|png|image-gen|external> --config config.json`
5. 嵌入架構圖到 docx

### Step 3：自動 sanity check

執行 `scripts/review_bcp_docx.py --input output/XXX.docx` 跑一輪靜態檢查，若有 🔴 問題先修再交付。

### Step 4：交付

- 檔案位置明確告訴使用者
- 附上「預設值 vs 你要自己填」清單（日期、版號、外點站等）

---

## 四、SOP — 模式 B（Review）

1. 讀取使用者給的 docx
2. 執行 `scripts/review_bcp_docx.py --input <docx>`
3. 檢查項目（內建規則詳見 `checklist/退件常見點.md`）：
   - 🔴 單位誤植（資訊室／資料治理科／氣象署）
   - 🔴 情境↔流程不一致（情境寫兩台、流程寫一台）
   - 🔴 MTPD／RTO／RPO 空白或寫「依實際作業」
   - 🔴 Table 7 銷毀程序空洞三項
   - 🔴 整合驗證缺 Log 檢視／佐證匯出（若是「計畫+佐證」一體文件）
   - 🟡 壹、目的有重複句
   - 🟡 完成時間欄空白／多餘空格
   - 🟡 人員表與聯絡表順序不一致
   - 🟡 術語大陸用語（技術棧／代碼／服務器／數據庫）
4. 按 🔴🟡🟢 分級列清單給使用者
5. 主動問：「要我直接 patch 這版嗎？」

---

## 五、SOP — 模式 C（Patch）

1. 接收：input docx + 修正項清單（或 Review 結果）
2. 執行 `scripts/patch_bcp_docx.py --input <docx> --fixes <json|list>`
3. 保留原格式、樣式、字型
4. 輸出修訂版到 `output/`

## 六、必守 Rules（實戰經驗）

### R1. 單位稱呼（水保署／農水保署文件）
- ✅ 用「減災監測組資訊管理科」（簡寫「資訊管理科」）
- ❌ 禁止出現：資訊室、資料治理科、氣象署、IT 部門
- 顧問稽核第一個就挑這個

### R2. 情境↔方式↔流程 必一致
- 三者措辭必對齊：
  - 若是一台主機合併 AP+DB：情境、流程表、段落全用「**備援虛擬主機**」一詞，不分「DB VM／AP VM」
  - 若是資料接收服務專案：不要出現「網站」「對外展示」「前端」字眼
- 這是這次顧問退件的本質問題

### R3. MTPD／RTO／RPO 必填數字
- 空白／「依實際作業」→ 一定退件
- 最壞情境超標三段套路：
  1. 寫出 RPO 目標值（依備份策略計算）
  2. 加【本次演練情境說明】：主系統+異地備份同時毀損之最壞情境，實際資料遺失量將超過 RPO 目標值
  3. 加改善建議：增加離線冷備份媒介／提高頻率／擴充異地備份點 → 納入後續矯正措施追蹤
- 這樣比空白加一萬分

### R4. 銷毀程序要具體
- ❌ 空洞三項：「刪除測試資料／執行實體檔案銷毀程序／報告」→ 退件
- ✅ 具體化：
  - 刪除方式：OS 層級移除 + 清空資源回收筒
  - 虛擬主機硬碟檔案：.vhd／.vhdx／.vmdk 整檔刪除
  - 書面佐證：**VM 申請表**（載明申請人、使用期限、銷毀時點）→ 由資訊管理科留存備查

### R5. 術語用台灣用語
| ❌ 大陸用語 | ✅ 台灣用語 |
|---|---|
| 技術棧 | 技術環境／平台規格 |
| 代碼 | 程式碼 |
| 源碼 | 原始碼 |
| 服務器 | 伺服器 |
| 數據庫 | 資料庫 |
| 數據 | 資料 |
| 默認 | 預設 |
| 軟件 | 軟體 |
| 視頻／视频 | 影片 |
| 打印 | 列印 |
| 硬盤 | 硬碟 |
| 內存 | 記憶體 |
| 文件夾 | 資料夾 |
| 賬號 | 帳號 |

### R6. 計畫書 vs 佐證分工
- 計畫書寫「會做什麼動作」（步驟、時限、負責人員）
- 佐證文件另一份，放實際 Log／截圖／匯出檔／銷毀紀錄
- 若使用者明確說「這份只是計畫」→ 可砍：
  - 整合驗證第 4、5 點（Log 檢視、佐證匯出）
  - Table 7 銷毀紀錄表步驟（用 VM 申請表代替即可）

### R7. 版號
- 不要自作主張升版（例如 V3.0 → V4.0）
- 先問甲方有沒有版號規則
- 常見：甲方以案件批號決定，維持 V3.0 是常態

### R8. 顧問退件的三大經典點
從本次協作整理：
1. **單位誤植**（資訊室／資料治理科 等）
2. **系統服務說明缺漏**（服務對象、重要性、中斷影響）
3. **系統架構圖沒附**（顧問會點名具體外點站如「松鶴」）

Mode A 從零產生時這三塊要預先寫好。Mode B Review 要特別掃這三點。

### R9. 一次問完原則
- 不要擠牙膏式逐題問
- 先盤點需要的全部輸入、列成群組、★◇ 標優先級，一次貼給使用者

## 七、檔案結構

```
~/.claude/skills/bcp-drill-doc/
├── skill.md                           本檔案
├── README.md                          使用範例
├── scripts/
│   ├── gen_bcp_docx.py                主產生器（吃 config.json）

│   ├── 必備欄位.md                     ISMS BCP 必備章節
│   └── 退件常見點.md                   顧問實戰挑過的點
└── examples/
    └── example_config.json            填好的 config 範例
```

## 八、速查

- **使用者說「寫 BCP」** → Mode A → 問卷 → 產 docx
- **使用者說「幫我看這份」+ 附 docx** → Mode B → review
- **使用者說「幫我改／gen 修訂版」** → Mode C → patch
- **使用者說「我不管流程直接給我結果」** → 用合理預設值走 Mode A，結尾列出所有假設讓使用者 review
