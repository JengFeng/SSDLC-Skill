# 需求說明書 + 經費概算表 Skill

替甲方撰寫需求說明書，同時產出對應的經費概算表。兩份合一個 .docx 輸出。

---

## 一、觸發時機

使用者說以下任一：
- 「寫需求書」「需求說明書」「需求規格」
- 「估價單」「報價」「經費概算」
- 「幫甲方寫」「發包」「招標」
- 討論到某系統要怎麼做 + 提到價格/費用

---

## 二、寫作風格（從範本分析）

### 語氣與立場
- **甲方立場**：「廠商應」「須」「得標廠商於...內提出」
- **規範性語氣**：不是在討論，是在規定。用「應」「須」「不得」
- **正式公文體**：「為確保...遂辦理...」「因應...需求」

### 句型特徵（從範本學到的）
- 開頭先說背景和目的，再展開工項
- 每個模組用一句話概述功能範圍，不展開技術細節
- 例：「開發空間圖台功能，包含多種底圖切換、確診與通報病例之即時分佈展示、人蚊風險整合地圖...」
- 用「含」「包含」「以及」串接多個功能點
- 維運條款用「若發生...須於...內完成」的條件句

### 用詞對照
- 說「開發」不說「建置」（開發模組、開發功能）
- 說「介接」不說「串接」（資料介接、系統介接）
- 說「配合機關」不說「配合客戶」
- 說「提送」不說「提交」（提送報告書）
- 說「決標次日起」計算天數
- 說「日曆天」不說「工作天」（除非特殊）
- 說「經審核通過後」觸發付款

### 格式特徵
- 大標用 Heading 1（計畫緣起、工作項目、專案時程等）
- 工作項目下分 Heading 2（各功能區塊）
- 細項用 List Paragraph（條列式）
- 不用編號「1.1.1」，用文字段落 + 條列

### 禁止事項
- 不寫技術實作方式（例如不說「用 Python 開發」「採用 PostgreSQL」）
- 不寫廠商的解決方案
- 不寫「我方」「本公司」（這是甲方文件）
- 禁用大陸用語（同 proposal-doc skill）

## 三、執行流程

### Step 1 — 需求蒐集

使用者提供需求（口述、會議紀錄或文件），我整理出：

```
需求摘要：
- 案名：___
- 甲方：___
- 總預算：___（使用者提供）
- 系統概述：___
- 主要功能模組：
  1. ___
  2. ___
  3. ___
- 維運需求：有/無
- 資安需求：有/無
- 期程：___
```

呈給使用者確認。

### Step 2 — 產出大綱

按照範本結構規劃大綱：

```
一、計畫緣起與目的
二、工作項目
  2-1 [主要功能區塊A]（含各模組）
  2-2 [主要功能區塊B]（含各模組）
  2-3 既有系統維運（若有）
  2-4 資訊安全
三、專案時程與里程碑
四、其他事項
五、驗收方式
六、保固
七、共同性規範
八、經費概算表
```

讓使用者確認大綱後再撰寫。

### Step 3 — 撰寫需求書

逐章撰寫，重點在第二章（工作項目）：
- 每個模組要說清楚功能範圍
- 用條列式描述每個功能點
- 不寫技術實作方式（那是廠商的事）
- 寫驗收標準（怎樣算完成）

### Step 4 — 經費分攤

使用者提供總價後，按以下邏輯分配：

1. 從總價反推：
   - 總價 ÷ 1.05 = 稅前總額
   - 稅前總額 × 約 95% = 工項可分配金額
   - 稅前總額 × 約 5% = 管理費
   - 差額 = 營業稅

2. 工項分配原則（按複雜度權重）：
   - 新系統開發/改版 → 佔比最高（40-50%）
   - 進階功能（AI/GIS/整合）→ 次高（25-35%）
   - 既有系統維運 → 中（10-15%）
   - 資訊安全 → 低（5-10%）

3. 各模組內再依功能複雜度細分

4. 金額取整（萬元或千元為單位）

5. 產出表格格式：

| 項次 | 內容 | 單位 | 數量 | 單價 | 總價 |
|------|------|------|------|------|------|
| 一 | [大項名稱] | | | | |
| 1 | [模組名稱] | 式 | 1 | xxx | xxx |
| 2 | [模組名稱] | 式 | 1 | xxx | xxx |
| 小計(一) | | | | | xxx |
| ... | | | | | |
| 合計 | | | | | xxx |
| 管理費(約5%) | | 式 | 1 | xxx | xxx |
| 營業稅5% | | 式 | 1 | xxx | xxx |
| 總計 | | | | | [=使用者給的總價] |

### Step 5 — 組裝輸出 .docx

用 python-docx 組裝，套用樣式。經費概算表用 Word 表格。

輸出到：`PROJECTS/{專案名稱}/待確認/`

## 四、固定模板章節

以下章節每案基本相同，直接套用：

### 專案時程與里程碑（固定）

付款比例：
- 工作執行計畫書：決標次日起 30 天，20%
- 期中報告書：決標次日起 180 天，40%
- 期末報告書：決標次日起 300 天，35%
- 驗收尾款：5%

### 驗收方式（固定）

- 計畫書採書面或審查會方式辦理
- 成果報告書 12 份
- 隨身碟儲存裝置 12 份

### 保固（固定）

- 驗收合格日次日起保固 1 年
- 系統功能瑕疵與錯誤修正
- 指派專案負責人員 1 名為聯絡窗口
- 保固期滿後 14 天內交付程式碼電子檔
- 檢視罰則後申退保固保證金（無息）

### 共同性規範（固定）

- 履約期間密切聯繫取得最新資料
- 配合出席相關會議並準備資料
- 審查會議費用含於服務費內
- 配合機關要求出席會議
- 各階段提送至少 10 份報告
- 審查意見 14 天內修正，審定 7 天內編製正式報告
- 不得採購中國大陸資通訊設備

### 其他事項（半固定）

- 系統運作環境由機關提供（伺服器、資料庫）
- 機關協助取得必要資料與授權

---

## 五、注意事項

1. 需求書是甲方立場，不是乙方
2. 不寫技術實作細節，只寫「要什麼」
3. 經費分攤要合理，不能某項特別高或特別低
4. 總價由使用者提供，我負責分配
5. 固定章節直接套，不需要每次重寫
6. 金額要取整，看起來專業
7. 需求書和經費概算表的工項要一一對應
8. 輸出前確認所有工項都有對應的報價項目
