## 第一章：資安稽核總覽

### 1.1 稽核目的與背景

內部資安稽核是公司依據 ISMS（資訊安全管理系統）要求，每年定期對在執行的專案進行資安合規性檢查。稽核目的在於確保每個專案在軟體開發生命週期（SDLC）中，遵循公司制定的資訊安全管理規範，包含版本控管、帳號權限管理、程式變更管制、弱點掃描、個資保護等面向。

稽核通常由公司內部資安團隊（或指定稽核人員）發起，針對當年度在執行中的專案，依據「備稽資料項目清單」逐項檢查。受稽專案的 SA（系統分析師）或 PM（專案經理）需在規定時間內備齊所有稽核佐證資料。

### 1.2 組織架構

資安稽核涉及的組織包含：

- **逢甲大學地理資訊系統研究中心**：母體組織
- **[廠商名稱]**：公司實體，地址為台中市西屯區河南路二段 262 號 B 棟 14F
- **關係企業**：天眼衛星科技、天思數位科技、易圖科技等（部分專案如 FEMA 涉及多個關係企業共同執行）
- **外部稽核單位**：114 年度起委由德欣寰宇公司進行稽核

### 1.3 稽核時程

根據歷年經驗，稽核流程大致如下：

- **稽核通知**：通常在每年 3 月至 4 月間發出，通知各專案準備備稽資料
- **資料準備期**：約 2 至 4 週，各專案負責人依檢核清單準備佐證
- **稽核執行**：由稽核委員逐項審查，可能進行訪談或實地查核。以 114 年度為例，逢甲大學 4/9 早上、準線公司 4/10 早上 09:30~12:30
- **缺失改善**：發現缺失後，需在指定期限內完成改善並提交佐證
- **結案報告**：稽核委員出具稽核報告，列入年度 ISMS 管理審查

### 1.4 受稽專案範圍

每年由公司高層或資安委員會決定受稽專案清單。受稽專案名單會以 Excel 檔「受稽專案.xlsx」正式公告。

## 第三章：項目 1 — GIT 版控權限審查表

### 3.1 稽核目的

確保專案的版本控管系統（Git）之帳號權限管理符合 ISMS 規範，包含權限分級、申請程序、定期審查等。

### 3.2 稽核要求（核心 4 點）

1. **合約成員與 GIT 權限一致性**：合約書中列出的團隊成員名單，必須與 GIT 專案實際的成員清單一致。不能有合約外的人擁有專案存取權限，也不應有合約內的人未被加入 GIT 專案。
2. **權限角色分級管理**：GIT 專案成員的權限必須依職責分級，不能所有人都是 Maintainer 角色。一般開發人員應設為 Developer，僅專案負責人或架構師設為 Maintainer 或 Owner。
3. **權限申請程序**：GIT 專案成員權限的新增、變更、移除，必須有正式的申請與核准程序，不得由任何人自行新增帳號。
4. **年度權限審查**：GIT 專案權限至少每年執行一次全面審查，確認是否有離職人員未移除、權限過高等問題。

### 3.3 需準備的佐證資料

#### 3.3.1 IT-04-042 帳號權限清查表

這是公司標準表單（文件編號 IT-04-042，版本 1.0，初版日期 109 年 4 月 10 日），需填寫以下資訊：

- 專案名稱與系統名稱
- GIT 平台資訊（如 GitLab 網址）
- 帳號清單：包含帳號名稱、使用者姓名、角色（Owner/Maintainer/Developer/Reporter/Guest）、建立日期、最後登入日期
- 審查日期與審查人員簽核
- 審查結果與改善事項

**重要：IT-04-042 可同時涵蓋 GIT 權限與資料庫（DB）權限。** 以 114 桃園智農專案為例，同一份 IT-04-042 帳號權限清查表中包含兩個區塊：

**GIT 專案權限區塊：**
- GITMagr（GIT 管理員）：Maintainer
- Tonytsai（資深工程師）：Maintainer
- Rocky（副總工程師）：Owner
- Sky（副處長暨副資訊長）：Owner
- Hua（資深系統分析師）：Maintainer
- Shammy（資深工程師）：Owner

**資料庫權限區塊：**
- 智農網站使用（AgriUser）：db_owner
- 王湘樺（gis.hua）：db_owner
- 樹木疫病網站使用（treeUser）：db_owner

權限代碼說明：R（Read）、A（Add）、W（Write）、I（Insert）、D（Delete）、ALL（完整權限）。

以 114 水權管理專案為例，GIT 成員包含：GITMagr、Tonytsai、Rocky、John、Sky、Ryanlee、Kazev、Cool、Frankliu、Shammy、Envie 等，審查日期 2025/05/26，審查人員為劉正富。

#### 3.3.2 GIT 成員截圖

從 GitLab 或 GitHub 後台截圖，需顯示：

- 專案名稱清楚可見
- 所有成員的帳號名稱
- 每個成員的角色/權限等級
- 加入日期（如平台有顯示）

#### 3.3.3 截圖範例說明

以 113 自行車入口網專案為例，截圖內容應包含 GitLab 的 Project Members 頁面，清楚顯示成員列表、角色（Owner、Guest、Moderator 等）、加入日期等資訊。檔名建議格式：「1.GIT 版控權限審查表(YYYY-MM-DD).png」。

### 3.4 常見缺失與改善建議

| 常見缺失 | 改善建議 |
|---------|---------|
| 所有成員皆為 Maintainer | 立即調整為 Developer，僅保留 1-2 位 Maintainer |
| 離職人員未移除 | 立即移除並留下移除紀錄截圖 |
| 無申請程序 | 建立 Google Forms 或 Email 申請流程 |
| 合約外人員有權限 | 確認是否為支援人力，若非則移除 |
| 從未做過年度審查 | 立即執行審查並填寫 IT-04-042 表單 |

### 3.5 不同專案情境處理

- **使用公司內部 GitLab**：直接從 GitLab 後台截圖
- **使用甲方 GitLab/GitHub**：請甲方提供成員清單截圖，或請甲方協助截圖
- **使用外部代管**：需額外說明代管平台的安全性與存取控管機制

## 第四章：項目 2 — 測試機 OS 帳號權限審查表

### 4.1 稽核目的

確保專案使用的測試機（Test Server）上的作業系統帳號權限，符合最小權限原則與帳號管理規範。

### 4.2 稽核要求（14 項檢核點）

1. **帳號個人專用**：測試機帳號應為個人專用，不得共用。每位需要存取測試機的人員都應有自己的帳號。
2. **系統帳號獨立控管**：服務帳號（如 IIS Application Pool 帳號、SQL Service 帳號）應獨立控管，不得用於一般登入。
3. **帳號異動需申請核准**：帳號的新增、修改、刪除均需經過正式的申請與核准程序。
4. **權限等級明確定義**：必須明確定義各帳號的權限等級，如系統管理員（Administrator）、標準使用者（Standard User）等。
5. **禁止全面授予管理員權限**：不得將所有帳號都設為 Administrator，應遵循最小權限原則。
6. **管理員帳號限制人數**：系統管理員帳號應限制人數（建議不超過 2 人）並加強控管，如啟用多因素驗證。
7. **離職異動即時移除**：人員離職或職務異動時，應立即移除或停用其帳號，不得延遲處理。
8. **保留稽核紀錄**：帳號登入與操作應保留稽核紀錄（Audit Log），以便事後追查。
9. **符合密碼安全政策**：帳號密碼應符合公司密碼安全政策，包含最小長度、複雜度要求、定期更換等。
10. **遠端連線限制來源**：遠端連線（如 RDP）應限制來源 IP 或要求透過 VPN 連線。
11. **長期未使用帳號清理**：長期未使用的帳號應定期清理或停用。
12. **測試與正式環境隔離**：測試環境應與正式環境完全隔離，不得共用伺服器或資料庫。
13. **每年至少一次權限審查**：每年至少執行一次全面的帳號權限審查。
14. **留存審查紀錄**：應留存審查紀錄與改善結果作為佐證。

### 4.3 需準備的佐證資料

#### 4.3.1 IT-04-042 帳號權限清查表

與 GIT 版控權限清查表使用相同的標準表單 IT-04-042，但填寫的是測試機 OS 帳號資訊：

- 測試機名稱/IP
- 帳號清單：帳號名稱、使用者姓名、權限等級（Administrator/Standard User）、建立日期
- 審查日期與審查人員

#### 4.3.2 測試機帳號截圖

需從測試機截圖，內容包含：

- 使用者帳號清單（「電腦管理」>「本機使用者和群組」>「使用者」）
- 帳號權限群組歸屬
- 帳號申請紀錄（如有 Google Sheets 管理表單則截圖）

以 114 資料平台專案為例，需準備：
- 測試機 OS 帳號清單截圖（顯示 Administrator、Guest、Ryan、Terry 等帳號）
- 帳號權限審查表截圖（Google Sheets 格式）
- 帳號申請紀錄截圖

#### 4.3.3 截圖命名規範

- 「2.測試機OS帳號([日期]).png」
- 「2.測試機OS帳號權限審查表([日期]).png」
- 「2.測試機OS帳號申請.png」（如有申請程序截圖）

### 4.4 特殊情境處理

#### 4.4.1 公司內部無測試機的情況

若專案的測試機不在公司內部（如測試機在甲方機房），處理方式為：

- 在資料夾內建立說明文件，註明「準線內部無該專案測試機（測試機在 [甲方名稱]）」
- 若能取得甲方測試機帳號截圖，仍應一併提供
- 若完全無法取得，需書面說明原因

以 115 水保審核專案為例，其說明為：「準線內部無該專案測試機（測試機在水保署）」。

#### 4.4.2 測試機帳號遵循組織 AD 管理原則

若公司有統一的 Active Directory（AD）帳號管理機制，可註明「依循組織 AD 管理原則」，並提供 AD 相關管理政策文件或截圖作為佐證。

## 第五章：項目 3 — 程式上版流程

### 5.1 稽核目的

確認專案是否建立正式的程式上版（部署）流程，以確保程式碼從開發到正式環境的過程受到適當管控。

### 5.2 稽核要求（13 項檢核點）

1. **程式變更的需求**：是否有明確的變更需求來源（如需求單、Bug 單）
2. **正式上版流程**：是否建立正式的上版流程（書面或系統化）
3. **變更申請與核准**：是否有變更申請與核准機制（如上版申請單需主管簽核）
4. **上版申請紀錄**：是否保留上版申請紀錄（含申請人、申請日期、核准人）
5. **測試環境測試**：是否於測試環境完成測試並留存紀錄
6. **版本控管系統**：是否採用版本控管系統（如 Git）
7. **版本變更紀錄**：是否保留版本變更紀錄（Git commit log 或 changelog）
8. **上版操作紀錄**：是否有上版操作紀錄（含時間、人員、版本編號）
9. **版本回復機制**：是否具備版本回復機制（Rollback），以便上版後發現問題可快速復原
10. **環境分離**：是否區分開發、測試、正式環境
11. **禁止直接修改正式環境**：是否禁止直接修改正式環境程式（需透過上版流程）
12. **緊急上版流程**：是否有緊急上版處理流程（hotfix 流程）
13. **定期檢視流程適當性**：是否定期檢視上版流程之適當性並持續改善

### 5.3 需準備的佐證資料

#### 5.3.1 上版流程說明文件

可以是以下任一形式：

- **流程圖**（建議使用 Mermaid、Visio 或 Draw.io 繪製）
- **文字說明**（逐步描述上版步驟）
- **截圖**（如使用 CI/CD 工具，截取 Pipeline 畫面）
- **Email 或信件截圖**（說明上版申請流程）

#### 5.3.2 不同專案的上版流程範例

**範例 A — 甲方有規定上版流程的專案（如 FEMA）**

> 「依據農村水保署上版規定實施」

這種情況下，只需說明遵循甲方的上版規定，並可附上甲方的上版流程文件作為佐證。

**範例 B — 公司自行管理上版流程的專案**

一般標準上版流程如下：

1. PG 完成功能開發，提交 Merge Request（MR）
2. SA 或 Lead Developer 進行 Code Review
3. 通過 Code Review 後合併至 develop 分支
4. 於測試環境部署並進行測試
5. 測試通過後，填寫「ISMS-0450 程式變更管制紀錄表」
6. 由 SA 或 PM 核准上版
7. 將程式碼合併至 main/release 分支
8. 部署至正式環境
9. 執行上版後驗證
10. 留存上版紀錄

**範例 C — 需要在甲方環境上版的專案（如國土測繪）**

國土測繪專案有獨立的上版流程，可能涉及甲方的資安審查與核准程序。佐證方式可為 Email 往來截圖（.msg 檔）或甲方提供的上版流程截圖。

### 7.1 稽核目的

確認專案的程式碼已經過原始碼安全檢測（Source Code Analysis）及/或網站弱點掃描（Vulnerability Scanning），且已針對發現的弱點進行修補。

### 7.2 稽核要求

- 專案應至少提供原碼檢測報告或弱點掃描報告之一（建議兩者皆有）

### 7.3 原碼檢測報告（Source Code Analysis）

#### 7.3.1 常用工具

- **Fortify（Micro Focus / OpenText）**：公司主要使用的原碼檢測工具
- **Checkmarx**：部分甲方指定使用
- **SonarQube**：開源替代方案

#### 7.3.2 報告類型

- **明細報告**：每個弱點的詳細說明，包含程式碼位置、弱點描述、修補建議

- `[系統名稱]_原碼檢測報告_明細.pdf`

### 7.4 弱點掃描報告（Vulnerability Scanning）

弱點掃描分為兩大類：**網站弱掃（Web Application Scanning）** 和 **主機弱掃（Host Vulnerability Scanning）**。

#### 7.4.1 常用弱掃工具

| 工具名稱 | 類型 | 實際使用專案 |
|---------|------|------------|
| Acunetix | 網站弱掃 | 114桃園智農 |
| Tenable Nessus | 主機弱掃 | 114桃園智農、114觀測站 |
| ISM 平台弱掃 | 網站弱掃 | 114水保審核（從 ISM 網站下載） |

以 114 桃園智農為例，同時具備三種掃描報告：Acunetix（網站弱掃）+ Fortify（原碼掃描）+ Nessus（主機弱掃），是最完整的範例。

以 114 觀測站為例，Nessus 掃描結果：掃描目標 dfm.ardswc.gov.tw（IP: 117.56.222.139），結果為 0 Critical、0 High、0 Medium、0 Low、15 Info。

#### 7.4.2 報告來源

- **ISM 網站下載**：部分甲方會透過資安管理系統（ISM）提供弱點掃描結果，可直接下載
- **自行掃描**：使用 Acunetix、Nessus、OWASP ZAP 等工具自行掃描
- **甲方委託第三方掃描**：由甲方委託資安廠商執行

#### 7.4.2 弱點掃描流程（初測→修補→複測）

1. **初測**：執行弱點掃描，產出弱點清單與修補建議
2. **修補**：依修補建議逐項修復弱點
3. **複測**：修補完成後再次掃描，確認弱點已修復
4. **佐證**：保留初測報告、修補佐證截圖、複測報告

#### 7.4.3 弱點修補佐證

對於每個弱點的修補，建議保留：

- **修補前後的程式碼差異**：Git diff 截圖或 commit 紀錄
- **修補佐證截圖**：展示弱點已被修復的畫面
- **誤判說明**：若弱點為誤判（False Positive），需提供說明

以 115 水保審核專案為例，部分弱點被判定為誤判：
- `弱點7_8_9_誤判_內網環境Cookie.png`
- `弱點7_8_9_誤判_外網環境Cookie.png`

這表示弱點 7、8、9 在內網與外網環境的 Cookie 設定不同，經比對後判定為誤判。

#### 7.4.4 弱掃報告的常見檔案格式

- `[URL]_網站修補建議.pdf`：針對特定 URL 的修補建議報告
- `[URL]_網站弱點清單總表.xls/.xlsx`：弱點明細清單（含弱點編號、嚴重程度、狀態）

## 第八章：項目 6 — 團隊成員電腦組態

### 8.1 稽核目的

確認專案團隊成員的開發用電腦符合公司資安規範，包含密碼政策、防毒軟體、系統更新等。

### 8.2 稽核要求（10 項檢核點）

1. **密碼符合複雜度政策**：Windows 密碼政策需啟用複雜度要求（含大小寫、數字、特殊字元、最小長度 8 碼以上）
2. **已設定自動鎖定螢幕**：螢幕保護程式或電源選項需設定自動鎖定（建議 5-15 分鐘）
3. **作業系統為支援版本**：不得使用已終止支援的 Windows 版本（如 Windows 7、Windows 8）
4. **系統已更新至最新**：Windows Update 需保持最新狀態
5. **已安裝防毒軟體**：需安裝公司指定的防毒軟體（如 Trend Micro Apex One）
6. **防毒已啟用且為最新**：防毒軟體需處於啟用狀態，且病毒碼為最新版本
7. **已開啟防火牆**：Windows 防火牆需開啟
8. **無未授權或盜版軟體**：不得安裝未授權或盜版軟體
9. **軟體皆為最新版本**：常用軟體需保持更新
10. **未安裝高風險軟體**：不得安裝可能造成資安風險的軟體（如 P2P 下載工具）

### 8.3 需準備的截圖佐證

## 第十章：項目 8 — 資料庫機敏資料保護方式

### 10.1 稽核目的

確認專案的資料庫中，對於個人資料或其他機敏資料，已採取適當的加密或保護措施。

### 10.2 稽核要求

- 需說明系統中個資或機敏資料的加密方式
- 若系統無個資，需明確聲明
- 若系統有個資，需說明加密演算法（如 AES-256）、加密範圍（哪些欄位）、金鑰管理方式

### 10.3 不同情境的處理方式

#### 10.3.1 系統有個資且採加密保護

**標準回應**：「系統個資採用 AES 256 加密演算法加密」

**佐證方式**：提供資料庫查詢截圖，展示加密欄位的內容為密文（十六進位的加密字串），而非明文。

以 114 國土測繪和 114 FEMA 專案為例，截圖應顯示資料庫查詢結果中，姓名（NAME）、電話（HOMETEL、OFFICETEL）等欄位為 `0x01FD196D3C690C925F6054B34C...` 格式的加密值。

#### 10.3.2 系統無個資

若專案系統完全不處理個人資料：
- 建立說明文件「8.資料庫機敏資料保護方式(本計畫無).txt」
- 內容註明「本計畫無個資處理」

以 113 自行車入口網專案為例：檔名直接標示「(本計畫無)」。

#### 10.3.3 委外廠商個資與資安保護責任

若涉及委外處理，需提供「ISMS-0442 委外廠商個資與資安保護責任」文件，說明委外廠商對個資的保護措施與責任歸屬。以 114 資料平台為例，提供 `8.資料庫機敏資料保護方式_ISMS-0442委外廠商個資與資安保護責任.pdf`。

### 10.4 加密方式技術說明

常見的個資加密方式：

- **AES-256（Advanced Encryption Standard）**：對稱式加密，金鑰長度 256 位元，為目前業界標準
- **加密範圍**：通常加密姓名、身分證字號、電話、地址、Email 等個資欄位
- **實作方式**：可在應用程式層（Application Level）或資料庫層（Database Level）進行加密
  - 應用程式層：在程式碼中對資料進行 AES 加解密後再存入 DB
  - 資料庫層：使用 SQL Server 的 Always Encrypted 或 Transparent Data Encryption (TDE)

### 10.5 各專案加密佐證方式彙整

| 專案 | 有無個資 | 佐證方式 |
|------|---------|---------|
| 114FEMA | 有 | 資料庫查詢截圖（8.個資採加密方式處理.png），顯示欄位為 0x 開頭密文 |
| 114國土測繪 | 有 | 資料庫查詢截圖，顯示 NAME、HOMETEL、OFFICETEL 等欄位為 AES 加密密文 |
| 114水權管理 | 有 | 加密證明截圖（8.加密證明.jpg），顯示 Pswd1、PswdCode、ApiKey、RightCode 等參數的加密輸出 |
| 114資料平台 | 有 | ISMS-0442 委外廠商個資與資安保護責任文件 |
| 113自行車入口網 | 無 | 檔名直接標示「(本計畫無)」 |
| 114台中水利 | — | 空 txt 佔位檔 |

注意：加密證明截圖可以是 .png 或 .jpg 格式，關鍵是要能清楚顯示加密後的密文內容。

### 10.6 資料夾結構


## 第十一章：項目 9 — PIA 隱私衝擊評鑑表

### 11.1 稽核目的

確認專案已依規定執行 PIA（Privacy Impact Assessment，隱私衝擊評鑑），識別個人資料的收集、處理、利用風險，並採取相應的保護措施。

### 11.2 PIA 執行流程

#### 11.2.1 步驟一：判定 PIA 是否必要

首先判定專案系統是否涉及個人資料：

- **無個資**：毋需進行 PIA，僅需在「IT-04-046 隱私衝擊評鑑工作表」中填寫「無需進行 PIA」
- **有個資**：需完整執行 PIA，並填寫兩份文件

#### 11.2.2 步驟二：填寫評鑑文件

**若系統有個資，需填寫以下兩份文件：**

1. **IT-04-046 隱私衝擊評鑑工作表**（.xlsx 格式）
   - 工作表包含：系統基本資訊、個資類別盤點、資料流分析、風險評估矩陣
   - Google Sheets 範本連結：`https://docs.google.com/spreadsheets/d/1ix4sObONhpfZAk2kyhjeS0T8SRlhdgkO`

2. **IT-04-047 隱私衝擊評鑑報告**（.docx 格式）
   - 報告包含：評鑑摘要、系統描述、個資處理說明、風險分析、改善措施

**若系統無個資，僅需填寫：**

1. **IT-04-046 隱私衝擊評鑑工作表**（.xlsx 格式）
   - 在工作表中勾選/填寫「無需進行 PIA」

### 11.3 IT-04-046 隱私衝擊評鑑工作表填寫要點

#### 11.3.1 系統有個資的情況

需詳細填寫以下區塊：

- **系統基本資訊**：系統名稱、系統描述、系統擁有者、系統管理者
- **個資收集項目**：列出系統收集的所有個資欄位（如姓名、身分證號、電話、地址、Email 等）
- **個資來源**：說明個資的來源（使用者自行填寫、其他系統介接、第三方提供等）
- **個資利用目的**：說明收集個資的目的
- **個資存取權限**：哪些角色可以存取個資
- **個資保護措施**：加密方式、存取控管、傳輸安全等
- **風險評估**：針對每個個資處理環節進行風險評估

#### 11.3.2 系統無個資的情況

以 114 觀測站專案為例：
- 檔名：`IT-04-046 隱私衝擊評鑑工作表_V1.0_114觀測站.xlsx`
- 在工作表中標註「本系統無個資處理，無需進行 PIA」

### 11.4 IT-04-047 隱私衝擊評鑑報告填寫要點

此文件僅在系統有個資時才需填寫，主要內容包含：

- **評鑑目的與範圍**
- **系統概述**：系統功能、使用者、資料流
- **個資盤點**：詳細的個資欄位清單
- **隱私風險分析**：識別的風險項目與嚴重程度
- **現有保護措施**：已實施的個資保護措施
- **改善建議**：需進一步改善的項目
- **結論**：整體評估結果

### 11.5 檔案命名規範

- 工作表：`IT-04-046 隱私衝擊評鑑工作表_V1.0([日期])_[專案名].xlsx`
  - 或：`IT-04-046 隱私衝擊評鑑工作表_V1.0_[年度][專案名].xlsx`
- 報告：`IT-04-047 隱私衝擊評鑑報告_V1.0([日期])_[專案名].docx`
  - 或：`IT-04-047 隱私衝擊評鑑報告_V[版次]_[專案名].docx`

日期格式通常為民國年月日 7 碼（如 1140407 = 114年4月7日）或 1150325。

### 11.6 IT-04-046 隱私衝擊評鑑工作表的完整分頁結構

以 114 疏濬管理專案的 V2.0 版為例，工作表包含 8 個分頁：

1. **分頁 1 — ISO 29134 隱私框架**：對應 ISO/CNS 29134 章節，填寫輸入（依據）與輸出（結果），最關鍵的是條款 6.2「判定 PIA 是否必要」
2. **分頁 2 — 個資處理資訊流**：描述 PII 當事人、PII 控制者、PII 處理者、第三方之間的資料流
3. **分頁 3 — 隱私風險評鑑分析**：列出風險項目（資安要素、資產識別、隱私風險、衝擊性、可能性、風險值），風險值 = 衝擊性值 × 可能性值 × 個資資產價值，超過 90 分為不可接受
4. **分頁 4 — 隱私風險地圖**：風險衝擊-可能性矩陣圖
5. **分頁 5 — 隱私風險改善控制措施**：針對不可接受風險提出改善措施
6. **個資盤點表**：詳細列出所有個資欄位（帳號、手機、身分證、Email、性別、生日、地址、銀行帳號、GPS、人臉辨識、健康資料等）
7. **個資範圍參考**：蒐集、儲存、處理、利用各階段的個資生命週期說明
8. **風險評鑑參考**：參考資料

### 11.7 IT-04-047 隱私衝擊評鑑報告的完整結構

以 114 疏濬管理和 114 桃園智農的實際報告為範例，IT-04-047 報告的標準結構如下：

**封面資訊：**
- 組織名稱（逢甲大學地理資訊系統研究中心 或 [廠商名稱]）
- PIA 過程/資訊系統/計畫名稱
- PII 控制者（通常是甲方）
- 報告日期、聯絡地址、聯絡人、電話、Email

**修訂履歷記錄：** 版本、日期、說明

**報告章節：**
1. **簡介**：PIA 目的、執行時間、參與人員、採用指導綱要（ISO/IEC 29134:2017）
2. **範圍**：處理目的、系統營運過程、管理人員（SA/PG/PM/PA）、利害相關者
3. **隱私要求事項（11 項）**：
   - 同意及選擇、目的適法性及法規、蒐集限制、資料極小化
   - 利用保留及揭露限制、公開透明及告知、準確性及品質
   - 個人參與及近用、可歸責性、資訊安全、隱私遵循
4. **風險評鑑**：10 項風險分析（機密性：側錄/未授權存取；完整性：竄改/未授權修改；可用性：伺服器異常/線路破壞）
5. **遵循性分析**
6. **風險處理計畫**
7. **結論及決策**：所有風險值是否低於 90 分

**無個資專案的特殊處理（以 114 桃園智農為例）：**
即使系統無個資，仍可填寫完整的 IT-04-047 報告。報告中明確標註：
- 處理目的：系統不蒐集使用者個資，無個資項目範疇
- 系統性質：對內系統，未開放對外服務
- 風險評鑑結果：無隱私風險
- 結論：評鑑結果無隱私資訊風險

## 第十五章：常見 Q&A

### Q1：如果專案今年沒有上版過，項目 4「程式上版紀錄」怎麼辦？

如果專案在稽核期間內確實沒有進行任何程式上版，可以在資料夾內放置說明文件，註明「本稽核期間內無程式上版作業」。但需確認是否真的沒有任何版本變更（包含 hotfix、安全修補等）。

### Q2：原碼檢測和弱點掃描都需要嗎？

理想情況下兩者都需要。原碼檢測（如 Fortify）檢查的是程式碼層面的安全弱點，弱點掃描（如 Acunetix）檢查的是已部署系統的安全弱點。若只能提供其中一種，需說明原因。部分甲方專案合約中會明確要求兩者皆需執行。

### Q3：GIT 權限中 Owner、Maintainer、Developer 的差別？

- **Owner**：專案擁有者，擁有所有權限，包含刪除專案
- **Maintainer**：維護者，可管理成員、合併 MR、管理分支保護規則
- **Developer**：開發者，可 push 程式碼、建立 MR，但不能管理成員或合併至受保護分支
- **Reporter**：只能查看程式碼，不能 push
- **Guest**：最低權限，僅能查看部分資訊

稽核要求大多數成員應為 Developer，僅 1-2 位為 Maintainer/Owner。

### Q4：測試機在甲方機房，我無法截圖怎麼辦？

有幾種處理方式：
1. 請甲方提供測試機帳號清單截圖
2. 透過遠端連線（如 VPN + RDP）自行截圖
3. 若完全無法取得，在資料夾內放置說明文件，說明測試機位於甲方機房且無法取得截圖，並提供甲方聯絡資訊作為佐證

### Q5：系統完全沒有個資，PIA 怎麼處理？

無個資的系統毋需執行完整 PIA。只需在 IT-04-046 隱私衝擊評鑑工作表中，填寫系統基本資訊並標註「本系統無個資處理，無需進行 PIA」。不需填寫 IT-04-047 隱私衝擊評鑑報告。

### Q6：ISMS-0450 程式變更管制紀錄表需要每次上版都填一份嗎？

是的。每一次程式上版至正式環境（或測試環境），都應該有一份對應的 ISMS-0450 紀錄表。這包含功能新增、Bug 修復、安全修補、定期維護等所有類型的變更。

### Q7：電腦組態需要團隊每個人都截圖嗎？

實務上通常只需一位代表人員的截圖即可（一般為 SA 或 Lead Developer）。但若稽核委員要求，可能需要多位成員的截圖。建議至少準備 1-2 位成員的完整截圖。

### Q8：弱掃報告中的弱點被判定為誤判，需要怎麼處理？

誤判（False Positive）需要提供佐證說明。佐證方式包含：
1. 截圖說明為何該弱點在實際環境中不存在
2. 提供環境配置截圖（如 Cookie 設定在不同環境的差異）
3. 書面說明誤判原因與判斷依據
4. 若甲方接受誤判結論，可附上甲方確認的 Email 或會議紀錄

### Q9：去年的備稽資料可以直接沿用嗎？

不建議直接沿用。每年的稽核應反映當年度的最新狀態：
- GIT 權限可能有變動（新增/離職人員）
- 測試機帳號可能有異動
- 電腦組態需反映最新的更新狀態
- PIA 可能因系統功能變更而需重新評估

但去年的資料可以作為「範例」參考格式和內容。

### Q10：資產盤點表（項目 10）需要準備嗎？

根據備稽資料項目資料夾中有一份「10.資產盤點表範本.xlsx」，但在標準 9 大項中並未包含。建議確認當年度的稽核通知是否有要求此項目。若有要求，則需依範本填寫專案使用的軟硬體資產清單。

### Q11：多個子系統的專案，文件怎麼組織？

若一個專案包含多個子系統（如 114 資料平台包含技研平台、歷史影像平台、資料平台、電子圖書管理中心），建議：
- 上版紀錄：按子系統分資料夾
- 原碼/弱掃報告：按子系統分別提供
- GIT 權限：若共用同一個 GitLab Group，可以合併一份
- PIA：通常以整個專案為單位填寫一份

### Q12：稽核時程通常多久？什麼時候要準備好？

根據歷年經驗，從收到稽核通知到稽核執行，通常有 2-4 週的準備時間。建議在收到通知後立即開始準備，不要等到最後。稽核準備說明簡報（如「資安稽核準備說明0325.pptx」）會說明具體的繳交截止日期。

### Q13：不同甲方對上版紀錄格式有不同要求怎麼辦？

以甲方的要求為主。例如：
- 水保署相關專案：使用甲方規定的上版流程
- 國土測繪專案：使用「資通系統維護紀錄單」格式
- 其他專案：使用公司標準的 ISMS-0450 格式

在稽核時，只要能證明有完整的變更管制紀錄即可，不限定使用哪種格式。

### Q14：版本回復機制（Rollback）需要什麼佐證？

版本回復機制的佐證可以是：
- Git 的 tag 管理截圖（顯示每次上版有對應的 tag）
- CI/CD Pipeline 的回復功能截圖
- 上版 SOP 文件中包含回復步驟的章節
- 過去實際執行過回復的紀錄（如有）

### Q15：資安稽核與甲方的資安要求有什麼關係？

公司內部的資安稽核是 ISMS 管理體系的一部分，主要確保公司整體的資安管理符合 ISO 27001 等標準。甲方的資安要求（如弱掃、原碼檢測）則是合約義務。兩者可能有重疊，但內部稽核通常更關注「管理面」（流程、紀錄、權限控管），而甲方更關注「技術面」（弱點修補、系統安全性）。

部分甲方（如農村水保署）會另外進行委外廠商稽核，這與公司內部稽核是分開的。內部稽核的資料可以重複使用於甲方稽核，但需依甲方的格式和要求進行調整。

### Q16：IT-04-042 帳號權限清查表可以同時包含 GIT 和 DB 權限嗎？

可以。以 114 桃園智農為例，同一份 IT-04-042 中包含 GIT 專案權限區塊和資料庫權限區塊。但也可以分開填寫，例如 115 水權管理和 115 資料平台就分別提供 GIT 和 OS 的獨立 IT-04-042 表。重點是所有帳號權限都要有審查紀錄。

### Q17：有些專案的上版紀錄是 PDF 格式而非 DOCX，可以嗎？

可以。以 114 觀測站為例，其 ISMS-0450 全部以 PDF 格式提供。關鍵是內容完整、有簽核，格式不拘。PDF 格式反而更好，因為不易被篡改。

### Q18：甲方要求的上版表單格式和公司標準不同怎麼辦？

以甲方要求為準。例如 114 桃園智農使用甲方的四表單制（02-013-01~04），114 國土測繪使用「資通系統維護紀錄單」。在公司內部稽核時，只要能證明有完整的變更管制紀錄即可，不限定使用 ISMS-0450 格式。

### Q19：弱掃報告除了網站弱掃，還需要主機弱掃嗎？

看甲方合約要求。以 114 桃園智農為例，同時提供了 Acunetix（網站弱掃）、Fortify（原碼掃描）、Nessus（主機弱掃）三種報告，這是最完整的做法。部分專案只需網站弱掃+原碼掃描即可。

### Q20：PIA 工作表版本 V1.0 和 V2.0 有什麼差別？

V2.0 版本（如 114 疏濬管理、114 觀測站使用）包含更完整的 8 個分頁結構，比 V1.0 更詳細。建議新專案直接使用 V2.0 格式。

### Q21：資訊服務申請單是什麼？需要提供嗎？

以 114 水權管理為例，提供了「3.4.資訊服務申請單.png」作為上版流程的佐證，截圖顯示 Windows 檔案總管中的多份 ISMS-3-AT40 申請單文件。這不是標準 9 大項的必要文件，但可作為「程式上版流程」的補充佐證，證明有正式的申請程序。

### Q22：CPS3 主機調整是什麼意思？

根據 114 年度資安內稽事項說明，CPS3 主機已調整為桃園計畫專用主機，原因是桃園計畫機房主機發現惡意活動，為避免橫向感染到其他單位主機。這屬於「遠端維護主機使用調整」的資安事件處理範疇，可能在稽核時被問到。

### Q23：專案的 txt 佔位檔全部都是空的代表什麼？

許多專案（如 114 台中水利、114 水保審核、114 高風險）的 9 個 txt 檔案全部為空（0 bytes），這代表該專案的稽核資料尚未開始準備。txt 檔案只是資料夾結構的佔位檔，實際的佐證資料（PDF、截圖、docx）應放在對應的子資料夾中。

## 第十六章：關鍵注意事項與稽核地雷

### 16.1 絕對不能犯的錯誤

1. **GIT 所有人都是 Maintainer**：這是最常見的缺失，必須在稽核前調整權限分級
2. **離職人員仍有系統權限**：不論是 GIT 或測試機，離職人員的帳號必須移除
3. **完全沒有上版紀錄**：即使過去沒有填寫，也必須回溯補齊
4. **弱掃有高風險弱點未修補**：高風險（High）以上的弱點必須修補或提供合理的誤判說明
5. **PIA 應做未做**：有個資的系統必須執行 PIA，不能遺漏

### 16.2 加分項目

1. 上版流程有視覺化的流程圖（而非純文字）
2. GIT 權限審查有定期執行的紀錄（不只是稽核前才做）
3. 電腦組態截圖完整涵蓋所有 10 項檢核點

## 附錄 C：個資法 11 項安全維護措施（PIA 教育訓練重點）

根據集團隱私衝擊評鑑教育訓練簡報，個資法要求的 11 項安全維護措施如下：

1. **組織人員與資源**：指定個資保護負責人與團隊
2. **個資範圍界定**：盤點組織內所有個資的蒐集、處理、利用範圍
3. **內部管理程序**：建立個資保護的內部管理制度
4. **風險評估**：定期進行個資保護風險評估（即 PIA）
5. **使用紀錄**：保留個資使用紀錄與軌跡
6. **資料安全**：對個資進行加密、存取控管等保護
7. **設備安全**：確保儲存個資的設備安全
8. **持續改善**：持續改善個資保護措施
9. **稽核機制**：建立個資保護的稽核機制
10. **教育訓練**：定期對人員進行個資保護教育訓練
11. **事故應變**：建立個資外洩事故的應變機制
