# 工作執行計畫書撰寫 Skill

把「服務建議書」轉成「工作執行計畫書」。建議書是競標說服用，計畫書是**得標後執行用**——所有內容都要落到可查核的數字（訪談定案、實際點位清單、ROI/告警閥值、驗證矩陣、硬體配置、期程與付款比例、月報、教育訓練時數）。

> 此案例情境：政府標案得標後，常於「決標日起 30 日曆天內」提交工作執行計畫書（含需求訪談會議紀錄、工作人員名單），須基於投標服務建議書、評選會承諾事項、議約條件修正，經機關核定後撥付契約總價約 10%。

---

## 一、定位與輸入鏈（最重要）

```
需求書(RFP)          → 要做什麼、驗收條件、期程框架、付款比例
服務建議書           → 怎麼做、技術方案、團隊承諾、平台功能
評選承諾 / 議約條件   → 評選會當場加碼或修正的事項（如有）
需求訪談結果         → 情境定案、點位清單、ROI、告警閥值、硬體（計畫書專屬，建議書沒有）
        ↓
工作執行計畫書        → 把上述收斂成「可執行、可驗收」的具體計畫
```

**與 proposal-doc（服務建議書）的本質差別：**

| 面向 | 服務建議書 | 工作執行計畫書 |
|------|-----------|---------------|
| 目的 | 競標說服、展現優勢 | 得標後執行、給機關核定 |
| 語氣 | 「我們能做、我們最強」 | 「我們要做這些、這樣驗收」 |
| 情境 | 情境池、概念方案 | 訪談**定案**的 N 項，逐項細到流程與閥值 |
| 點位 | 約略、預留擴充 | 候選盤點 → 篩選 → 正式導入清單（逐點） |
| 驗證 | 提 P/R/F1 指標 | 完整驗證矩陣：樣本數、日夜比例、達標%、排除條件 |
| 硬體 | 概述 | 配置表（設備/規格/數量/用途） |
| 期程 | 甘特圖概念 | 階段表對應交付與付款%、月報機制 |

## 二、寫作風格規則（繼承 proposal-doc）

### 語言與用語
- 繁體中文、台灣用語。禁用大陸用語：軟件→軟體、視頻→影片、信息→資訊、網絡→網路、用戶→使用者、登錄→登入、獲取→取得、應用程序→應用程式、屏幕→螢幕。
- **術語全文統一**：同一概念全文用同一個詞，不可混用。常見地雷：閾值 vs 閥值（二擇一、全文一致）、攝影機 vs 鏡頭、站點 vs 點位、辨識 vs 識別。

### 禁用詞彙
- 深入探討 / 全面 / 綜合 / 強健 / 賦能 / 利用(說「用」) / 值得注意的是 / 總之 / 綜上所述 / 無縫 / 打造 / 痛點 / 落地 / 生態系統
- 開場清喉嚨：眾所周知 / 不難發現 / 在當今…的時代 / 隨著…的發展
- 空心強調：不僅…更… / 毋庸置疑 / 不可否認

### 禁用句型結構（AI 痕跡）
1. **擬人化無主詞**：別讓系統/資料/效益自己做動作。每句要能答「誰、用什麼、做了什麼、量化結果」。
2. **二元對立「不是X而是Y」** → 直接講 Y。
3. **否定排比「不是A不是B而是C」** → 直接講 C。
4. **空泛宣稱「效益顯著/影響深遠」** → 補上數據。
5. **極端詞（完全/所有/永不/絕對）** → 改成可驗證範圍。

**計畫書實測常見殘留（demo 回饋，務必補抓）：**
- 「○○為系統核心 / 是關鍵」開場 → 改寫成該層/該模組「負責做什麼」（擬人化＋空泛宣稱）。
- 「形成…完整處理鏈 / 完整鏈路 / 閉環」收尾 → 刪「完整」，直接列步驟即可（空心強調）。
- 「取決於…是否 / 為確保…」通則式清喉嚨開場 → 直接寫「本案依下列…」。
- 「使值班人員…即可研判 / 即可掌握」替使用者代言效益 → 只陳述系統輸出，不替對方下結論。
- 趨勢式收尾「隨運轉資料累積而提升」 → 補觸發門檻數字（如每滿 N 張或每季再訓練一次）。

### 計畫書專屬硬規則：一切落到可查核
- 點位要給「數量 + 清單」（不寫「多個點位」，寫「正式導入 40 組，清單如表」）。
- 驗證要給「樣本數 + 比例 + 達標% + 排除條件」（不寫「準確率高」，寫「100 張影像、日夜各 50、P/R/Accuracy 三項均須 ≥80%」）。
- 期程要給「期限 + 對應交付 + 付款%」。
- 教育訓練要給「場次 + 時數 + 課程內容」。

### 交付前評分閘（每章五維各 1-5，低於 20/25 改寫）
具體度（有數字/清單/閥值？）、主詞明確、句型（無五類 AI 句型）、用語（台灣用語無禁用詞）、可驗收（機關能照此驗收嗎？）。

### 刻意不採用
- 不砍光副詞（保留分寸詞：適度/初步/必要時）；逐條列舉是對的；被動語態在引法規/既有架構時可用；不寫短促格言體。

## 三、章節骨架（依黃金範本 工作執行計畫書_0529v3）

### 第一章　需求訪談與導入規劃
- **第一節　需求訪談**：訪談對象、目的、結論摘要 +〔表〕需求訪談彙整表（辨識類別 / 主要需求 / 說明）
- **第二節　AI辨識情境規劃**：依訪談**定案**的 N 項情境，逐項寫：
  - 辨識目標與處數（例：虛擬水尺 35 處、漂浮物 3 處、積淹水 8 處）
  - 技術說明（核心引擎如 SAM3 / YOLO / VLM-LLM；運作流程逐步驟 + 流程圖）
  - 告警條件與預期成果（閥值、觸發動作、LINE 推播）
  - **驗證方式**（見第六節驗證方法論）
  - 必要時點出辨識不易站點（夜間/遮擋/距離過遠）並附示意圖
- **第三節　辨識站點規劃**：一、候選點位盤點〔表〕→ 二、初步篩選結果〔表〕→ 三、正式導入 N 組點位規劃〔表〕（項次/編號/站名/分類）
- **第四節　告警通知規劃**：〔表〕類型 / 告警方式 / 頻率 / 重複發送 / 展示

### 第二章　系統規劃
- **第一節　系統整體架構**（依 Benson 慣例放**一對架構圖**，缺一不可）：
  - **系統架構圖**：邏輯/模組分層（影像接入層 / AI運算層 / 監控管理平台層）
  - **整體架構圖**：端到端資料流「哪來哪去」＋硬體（攝影機 → 封閉光纖專線VPN → 機房主機 GPU/應用伺服器HA/儲存 → 平台/資料庫 → Web儀表板/LINE推播/開放API對接外部平台）
- **第二節　硬體配置**：〔表〕設備 / 規格 / 數量 / 用途（廠商自提雲端或地端，對應 RFP）
- **第三節　平台功能規劃**：逐功能寫（典型七項：儀表板總覽、即時影像監看、異常偵測與事件通報、歷史查詢、報表匯出、API 服務、系統管理）+ 各功能模擬畫面
- **第四節（或第五節）　告警情境說明**：情境模擬 — AI 辨識異常 → LINE 推播（含當下單張影像）→ 即時查看 → 處理狀況通報 → 平台更新事件狀態

### 第三章　AI模型訓練
- **第一節　模型開發流程**：〔表〕步驟 / 階段名稱 / 工作內容
- **第二節　資料蒐集策略**：〔表〕條件類別 / 蒐集說明（白天/夜間/雨天/颱風多情境）
- **第三節　資料標註**：標註規範、工具、品檢（雙人複核）
- **第四節　模型準確率驗證**：〔表〕指標(P/R/Accuracy) / 說明 / 用途；〔表〕辨識情境 / 判定正確定義 / 達標標準；〔表〕排除條件
- **第五節　持續改善機制**：人工確認/修正回收為新樣本 → 再訓練 → 再部署的閉環

### 第四章　期程規劃與交付項目
- **第一節　專案期程**：〔表〕階段 / 期限 / 主要工作內容（對應決標日 +30/+150/+360 等）
- **第二節　階段交付成果**：〔表〕期限 / 交付成果（對應付款比例 10/40/40/10）
- **第三節　每月工作報告機制**：每月 10 日前繳上月工作報告，內容含進度%/開發說明/困難因應/協作事項/下月預定

### 第五章　教育訓練
- **第一節　教育訓練規劃**：〔表〕訓練課程 / 建議時數 / 訓練內容；每年至少 1 場系統操作訓練（錄影留存）+ 1 場 AI 通識講座

> 章節順序與節名依案子微調，但「訪談定案 → 站點清單 → 系統與硬體 → 模型驗證 → 期程交付 → 教育訓練」這條主線要在。

## 四、驗證方法論（計畫書的靈魂，務必內建）

每個 AI 辨識情境的「驗證方式」用統一格式寫，這是機關驗收的依據：

1. **測試策略**：採情境矩陣，從歷史與即時影像選取 **100 張可辨識有效影像**做準確度分析。
2. **樣本比例**：日間 50 張 + 夜間 50 張；或 異常 50 張 + 正常 50 張（依情境）。
3. **效能指標**：計算混淆矩陣（Confusion Matrix），產出精確率（Precision）、召回率（Recall）、整體準確率（Accuracy）。
4. **達標標準**：三項指標均須 ≥ 80%。積淹水/漂浮物特別要求 Recall 達標（不漏報真實事件）。
5. **樣本納入/排除條件**：須為「人眼可合理辨識」之影像；排除 — 夜間無輔助光源致過暗、雜草嚴重遮擋、攝影機距離過遠致像素不足、密集波紋致模糊。

## 五、執行流程

### Step 1 — 讀輸入、抽已知
讀 RFP + 服務建議書（+ 評選承諾/議約條件如有），抽出：辨識情境池、技術方案、平台功能、期程框架、交付與付款比例、資安等級、主機需求。摘要呈使用者確認。

### Step 2 — 列訪談缺口、向使用者補資料
計畫書比建議書多的是「訪談才會定案」的東西。列清單問使用者（沒有就標 TODO 待訪談）：
- 定案的辨識情境是哪幾項？各情境點位數？
- 候選點位清單、篩選結果、正式導入 N 組清單？
- 各情境 ROI 與告警閥值？
- 硬體配置（設備/規格/數量）？
- 驗證樣本數與達標標準（預設 100 張 / 日夜 50/50 / ≥80%）？
- 教育訓練場次與時數？

### Step 3 — 產出大綱
依第三節骨架 + 訪談定案的情境數，產章節大綱（含各表清單），呈使用者確認後動筆。

### Step 4 — 逐章撰寫
- 每寫完一章呈使用者確認再續。
- 表格用實際數據填，不留空泛描述。
- 缺訪談資料處明確標〔待訪談補實〕，不要瞎掰數字。

### Step 5 — 圖片規劃與生成
沿用 image-gen / proposal-doc 的生圖規範（**經確認才生圖**）。常見圖：各情境辨識運作流程圖、辨識結果示意圖、辨識不易站點示意圖、**系統架構圖＋整體架構圖（資料流+硬體）一對**、平台各功能模擬畫面、硬體/網路部署圖、告警情境流程圖。架構圖務必成對：一張講系統（模組分層），一張講整體（哪來哪去＋硬體）。
- 有文字版：Nano Banana 2（中文正確）；純圖片版：gpt-image（最便宜可用 quality=low）。

### Step 6 — 組裝 .docx + QA 評分閘
- python-docx 組裝，套樣式（章=Heading1、節=Heading2、小節=Heading3、表用 Table Grid）；A4，上下 2.5cm、左右 1.9cm；CJK 字型微軟正黑體。
- 過 QA：每條 RFP 驗收項都有對應、所有數字/清單/閥值就位、無禁用詞與 AI 句型、表格編號連續、圖前有引導文字圖後有標號。
- 跑交付前評分閘（五維），低於 20/25 的章節改寫。
