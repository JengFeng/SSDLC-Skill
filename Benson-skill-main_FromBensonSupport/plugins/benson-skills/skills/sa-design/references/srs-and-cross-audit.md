# 正規 SRS 結構 + 工程師可照刻深度 + 交叉稽核自檢

> 這份是 sa-design 的「升級層」：當案子要交一整套可開發＋可送審的系統開發文件（不只一份 SA 系統分析設計）時照這個做。核心三件事：①照機關 SRS 查檢表結構 ②做到「工程師看了就能刻」的深度 ③產完一定跑「交叉稽核自檢」——不靠外部 AI 幫你檢。

---

## 一、系統開發文件套件（純開發 = 9 份；對外可整合成一份正規 SRS）

| # | 文件 | 回答什麼 |
|---|------|---------|
| 01 | 需求書 SRS/URS | 要做什麼、範圍、需求項 |
| 02 | 雛形畫面 | 畫面長怎樣（bootstrap-ui） |
| 03 | SA 系統分析設計 | ER／資料字典／架構／API／流程 |
| 04 | 功能規格書（模組設計） | 每個功能怎麼運作 |
| 05 | 畫面規格書（UI 細部） | 每個畫面每個元素怎麼刻 |
| 06 | WBS 開發任務拆解 | 排工/相依/工時/里程碑 |
| 07–09 | 測試計畫＋測試案例＋UAT 驗收 | 怎麼測、怎麼驗收 |

> 「正規 SRS（00b）」＝把 01/03/04/05 依機關查檢表整合成一份。設計層 02/03/04/05 互補不重複：雛形=外觀、SA/SD=資料與系統、功能規格=行為、畫面規格=畫面細節。

## 一之二、★操作層：開發任務看板（完整套件「必出」，別只丟規格）

> 踩過最痛的雷：規格寫得再細，工程師仍「**不知道現在做哪個任務、看哪份文件**」。一堆 reference 文件＝「查的東西」，但沒有「驅動做事」的操作層。**完整套件除了規格，一定要產「開發任務看板」：**

- **★ `00 開發任務看板`（`scripts/render_board.py`）**：每支功能=一列任務，可點狀態（待開發/開發中/完成，存 localStorage、頂部即時統計），每列深連 `04_功能規格書.html#FS`／`05_畫面規格書.html#SCR`／`07`；最上面一組「**地基**」任務（建表/seed/API 骨架，指向 03）。**由上往下做＝開工順序**。這是工程師「每天開的那一頁」，也是整套的入口 —— 每份文件頂部導覽列的「家」就指向它。
- （選配）`render_portal.py` 文件總覽頁：看板已是入口、每份文件頂部又有導覽列可互跳，故總覽頁多餘，**通常不產**。

**為了深連，spec 文件渲染要加錨點**：`render_fs.py` 功能卡輸出 `id=FS_code`、`render_scr.py` 畫面卡輸出 `id=SCR_code`（已內建）。

### 套件渲染 pipeline（全共用 `scripts/doc_common.py` 暖色樣式＋頂部導覽列；系統名讀 `SA_SUITE_TITLE`）

```
export SA_SUITE_TITLE="XX 系統"
python scripts/transform.py   model.json sa_spec.json            # 正規模型→ER+資料字典（同源，保證 ER↔字典一致）
python scripts/render_sa.py   sa_spec.json     03_SA系統分析設計.html
# （選配·03 加值）python scripts/gen_schema.py model.json db_schema.sql   # 匯出 CREATE TABLE DDL，地基建表直接跑
python scripts/render_fs.py   fs_result.json   04_功能規格書.html        # 功能卡帶 id=FS 錨點
python scripts/render_scr.py  scr_result.json  05_畫面規格書.html        # 畫面卡帶 id=SCR 錨點
python scripts/render_wbs.py  wbs_result.json  06_開發任務拆解WBS.html
python scripts/render_test.py test_result.json [輸出資料夾]   # 一支吐三檔：07_測試計畫/08_測試案例/09_驗收文件
python scripts/render_srs.py            # 00b 整合（讀 fs_result/result/sa_spec/scr_result/test_result）
python scripts/render_audit.py          # 00c 健檢（preflight 程式硬檢查＋既有語意稽核結果）
python scripts/render_board.py fs_result.json  00a_開發任務看板.html    # ★ 操作層核心＝入口：規格→任務（必出）
# （選配）python scripts/render_portal.py        # 文件總覽頁；看板已是入口，通常不需要
```

> 各 render 吃的 JSON（functions/screens/wbs/tests schema）由「完整套件 SOP 的 Workflow」（建模→功能清單→逐功能/逐畫面/WBS/測試）產出。`render_srs.py`／`render_audit.py` 內含預設背景/名詞 prose，依案調整。

## 二、機關「軟體需求規格書 SRS」查檢表結構（對外正規版照這個章節）

```
1 前言：1.1 文件目的 / 1.2 文件使用者 / 1.3 相關文件
2 概述：2.1 專案目的 / 2.2 專案範圍
3 背景說明：3.1 現行系統 / 3.2 現行使用者介面 / 3.3 硬體環境 / 3.4 軟體環境
4 需求規格：
  4.1 使用者需求（4.1.1 需求清單 / 4.1.2 非功能性需求 NFR）
  4.2 系統功能結構圖   ← 用 FN 編碼（FN1→FN11…，見三）
  4.3 使用案例圖 Use Case Diagram   ← 最常被漏，務必出
  4.4 事務流程圖 Business Flow
  4.5 系統功能模組說明（每模組四件，見四）：
      4.5.1 Use Case 說明 / 4.5.2 螢幕格式·畫面雛型＋欄位說明表 / 4.5.3 報表格式 / 4.5.4 計算處理邏輯
  4.6 系統介面說明（資料流向＋Special Req＋User/Hardware/Software/Communication Interface）
  4.7 系統環境架構（硬體圖＋軟體圖；無實際環境就標「假設·待 IT 確認」）
5 附錄：5.1 訪談紀錄 / 5.2 名詞解釋 / 5.3 需求追溯表（R→FN→FS→TC）
```
URS＝讓客戶確認；SRS＝讓開發團隊掌握設計方向。

## 三、FN 功能編碼 + FN↔FS 對照（雙編碼必給對照表）

- 系統功能結構用 **FN 編碼**：FN1（大模組）→ FN11、FN12…（葉功能）。
- 功能規格/畫面/測試常用另一套碼（FS-*、SCR-*、TC-*）。**只要存在兩套碼，就一定要給一張對照表**（放 SRS 5.3 或功能規格首節），否則追溯斷、工程師對不上。
- 一個 FN 若在功能規格被拆成多支 FS（例 FN36 設定/通知/帳號 → FS-A05 通知＋FS-A06 帳號），要明寫「13 FN ＝ 14 FS（FN36 拆 2 支）」，別讓「功能數」在 FN 軸與 FS 軸混用。
- ⚠ FN 編碼是「分類分段」（FN1x 民眾／FN2x 廠商／FN3x 機關／FN4x 共用），不是流水號。FN42 = FN4 分類下第 2 項，是合法編號，別誤判為「超出 13 的錯誤」。文件最好在結構圖旁註明編碼規則。

## 四、「工程師可照刻」深度標準（看了就能做，不是名稱+資料表）

1. **輸入欄位說明表**（每個輸入畫面都要）：
   | 欄位 | 說明(這欄做什麼用) | 長度 | R/W | 預設值 | 屬性(必須輸入/下拉選單) | 備註 |
2. **Use Case 說明 四段**：Brief Description / Pre-condition / Basic Flow(逐步, 標對應畫面) / Post-condition / Special Requirement / Reference
3. **畫面規格逐元素**：每個欄位/按鈕/清單 → 元件型別 / 必填 / 資料來源綁定 / 驗證·互動行為；外加「畫面元素 → API → 資料表.欄位」對應表＋送出後行為。
4. **報表格式**、**計算處理邏輯**（矩陣怎麼存、異常怎麼變工單…）要寫出來。
5. 判準：工程師「看起來對、細看全錯」就是深度不夠——欄位用途/驗證/綁哪支 API 哪個欄位沒講清楚。
6. **受控清單必附明細**：凡寫「N 類/N 種/N 個」的受控詞彙，同一套文件內必有一處列出全部 N 項明細（表格或對照表），並標清楚計數規則（哪些算一項、有無合併項）。只給數字不給明細 = 不合格。
7. **狀態要有欄位**：凡規格描述「依狀態判定/不可跳關/未齊不可送/逾期」，資料字典必有對應 status 欄位（enum）＋時間戳，不能只靠某文字欄位是否為空來反推。

## 五、⭐交叉稽核自檢（產完必跑，不靠外部 AI）

> 多份文件＝一張互相牽動的網。**單份寫得對 ≠ 整套對得起來。** 產完／每次改完都要跑這個，跑到「真結構問題＝0」。

### 鐵則：能用程式硬判的，先硬判（不要全丟 LLM）

LLM 語意稽核會「看心情」——同一份文件這次抓到、下次漏掉（山豬湖案實測：ER 漏畫 ROLE_PERMISSION、九大模組懸空引用 都本該被維度 3/5 抓到卻漏網）。
所以 `cross_audit.js` v2 先跑 `preflight()` 程式正則硬掃，把「鐵證型」結構問題 100% 穩定抓出，再交給 LLM 補語意層。
凡是「正則就能判真假」的，一律寫進 preflight，不要寄望 LLM 自覺：
- ER 圖實體 vs 資料字典表名（字典有、圖沒畫）
- FN↔FS 雙編碼是否鄰近並列（缺對照）
- 「對齊 X 大模組」這類錨點，回查來源是否真有 X（懸空引用）
- 同一指標（表數/API 數/案例數/版號）跨文件是否兩種值

### 10 個稽核維度（每維度一個獨立 agent，附證據、對抗式）
1. **功能編碼**：FN↔FS↔SCR↔TC 是同一批功能、對得上
2. **畫面引用**：各文件引用的畫面，畫面規格 SCR 清單都真的有（雙向）
3. **資料表/JSON 欄位**：FACILITY/schema_json/result_json(每格含 facility_id)/…各文件同一套；**ER 圖必須跟資料字典同欄位（最常漏：ER 漏欄/漏表）**
4. **API 端點**：SA/SRS/功能/畫面/WBS 端點與支數一致（含上傳等）
5. **需求追溯鏈**：R→FN→FS→SCR→TC 串得起來、不斷點
6. **數字**：功能數/表數/畫面數/案例數/工時/版號——同一數字不能有兩種值
7. **狀態機＋基準決議**：狀態流轉、以及各項已定案決議，各文件同一說法
8. **受控詞彙完整性**：文件反覆引用的「受控清單」（如 0611 版 16 類巡檢表、角色清單、頻率清單），必須在至少一份文件「完整列出明細＋對照表」，不能只報數量。⚠ 計數陷阱要明標：如「緊急（豪雨、颱風及地震後緊急巡查）」含頓號，須標明「此為單一張表」，否則機械拆分會把 16 類誤算成 17。山豬湖案：SRS 反覆引用「16 類」卻從不列明細，明細只在需求說明書。
9. **狀態欄位完整性**：凡功能規格要求「狀態判定」的（簽核未齊不可送、工單狀態流轉、逾期判定），資料字典必須有對應的「結構化狀態/時間欄位」可供程式判定。只存姓名/文字字串、無 status 或時間欄位 → 報結構落差。山豬湖案：三方簽核只存姓名 NVARCHAR(50)，無簽核時間/狀態，「簽核未齊不可送」無欄位可判。
10. **商務範圍對齊**（跨商務文件）：報價單/經費表的「收費項目」與 SRS/WBS/功能規格的「本期交付範圍」必須對齊。抓兩種病：①收費項卻列二期/本期不交付 ②綑綁項夾了二期子項卻沒切交付邊界。山豬湖案：報價第 5 項綑綁「既有平台整合＋部署＋教育訓練＋保固」，其中「既有平台整合(FN42)」標本期不交付。

### 收緊規則（關鍵：否則不會收斂）
- LLM 語意稽核用寬鬆規則**永遠抓得到東西、不會到 0**（會挑同義詞、排版順序；數字會跳如 28→13→22）。
- 規則務必收緊成「**只報結構性**」：代號對不上／欄位差／API 差／追溯斷／數字兩種值／決策矛盾。
- **明確排除純風格**：同義詞/量詞（「16 表」vs「16 類」）、章節順序、標點、潤飾建議——一律不報、判 consistent。
- 收緊後就會收斂（實測 22→4→1→0）。

### 怎麼跑
- 先程式硬掃：`cross_audit.js` v2 內建 `preflight()`，改頂部 `FILES` 絕對路徑即可。preflight 100% 穩定抓鐵證型（ER 漏表/FN-FS 對照/懸空錨點/數字口徑/版號）。
- 再 LLM 語意：同檔 10 維度用 Workflow 多 agent 並行，每維度一個 agent、structured schema 回 {dimension, consistent, issues[{severity,docs,problem,evidence,fix}]}。
- 拿結果：**真結構問題(高/中) → 直接修 build 腳本重生、修到 0**；純用詞(低) → 列給使用者判斷、不無限重跑。
- 改完用**同一稽核複跑**確認收斂。

## 六、改文件鐵則
- **改上游必查下游貫穿**：改了 SA/SRS 的核心（如 result_json 加欄、公式改、決策定案），畫面規格/測試/WBS 常沒跟上 → PG 照舊的做就錯。宣告完成前必跑交叉稽核，別只查改的那份。
- **ER 圖 = 資料字典**：兩者欄位要一致（EF Core 照 ER 或字典建表都不能少欄）。
- **數字單一真實來源**：功能數/表數/案例數/版號 改一處要全文同步。
- 生成式文件：改 build 腳本（spec）重生，版次+1、修訂紀錄+1 行。
